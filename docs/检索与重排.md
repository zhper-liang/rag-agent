# 检索与重排

## 1. 目标

根据[用户问题预处理](用户问题预处理.md)产出的查询，从 Milvus 里找出最相关的 chunk，重排后交给[上下文构造](上下文构造.md)：
- 混合检索：稠密向量（DISKANN）和 BM25 在 Milvus 内加权融合。
- 重排：bge-reranker-v2-m3，文本和图片在同一个列表里一起排。
- 上下文扩展：把命中 chunk 的前后 chunk、代码引导段落、关联图片一次取回来。
- Grade：只看重排分数，决定通过、改写重试，还是回答“资料不足”。

输入（来自预处理）：
- `standalone_question`：指代消解后的完整问题，用于重排
- `queries`：1~3 条检索查询（改写 / 扩展），用于召回
- `filters` / `soft_filters`：硬过滤（接口参数）和软过滤（从问题里识别），检索时用 `effective_filters` 合并；重试时软过滤会被去掉，见[用户问题预处理](用户问题预处理.md) §8.3

输出：
- `hits`：最多 8 个命中 chunk，带重排分数
- `expansions`：每个命中 chunk 的扩展内容（前后 chunk、引导段落、附件图片、图片锚点）
- `top_score`：最高重排分数，grade 用

## 2. 流程

```
queries（1~3 条）
  ↓ 批量编码成查询向量（编码服务，一次调用）
  ↓ 每条查询并发执行 Milvus hybrid_search：
  │    稠密（DISKANN，search_list=100）top50 + BM25 top50
  │    WeightedRanker(0.7, 0.3)，过滤 searchable == true + 用户过滤条件
  │    只返回 chunk_id / doc_id / version / type 等轻量字段
  ↓ 多查询合并：同一 chunk 取最高分 → 只保留每个文档的最新版本 → 内容去重 → 取前 30
  ↓ 回表：按 chunk_id 批量取 embed_text、text、content_hash 等字段
  ↓ 重排：(standalone_question, embed_text) × 30，一次调用
  ↓ 筛选：分数 < 0.3 丢弃 → 每个文档最多 3 条 → 取 top 8
  ↓ 上下文扩展：收集前后 chunk / 引导段落 / 图片 id → 一次批量查询取回
  ↓ grade（条件边）：
       top_score ≥ 0.5              → build_context
       否则 retry_count < 2         → rewrite → 重新检索
       否则                         → fallback（回答“资料不足”）
```

## 3. 参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `dense_top_k` / `sparse_top_k` | 50 / 50 | 每条查询每一路的召回数 |
| `search_list` | 100 | DISKANN 检索时的候选列表长度，必须 ≥ top_k；调大召回升高、延迟变长 |
| `weights` | 稠密 0.7 / BM25 0.3 | 初始值，评测集上在 0.5~0.8 之间调 |
| `per_query_limit` | 50 | 每条查询融合后保留的数量 |
| `candidates` | 30 | 多查询合并后送进重排的数量 |
| `rerank.max_length` | 512 | 问题 + 片段的最大 token 数 |
| `rerank.threshold` | 0.3 | 归一化（sigmoid）后低于该值的丢弃 |
| `rerank.per_doc_cap` | 3 | 每个文档最多保留几条，避免单个文档占满结果 |
| `rerank.top_n` | 8 | 最终命中数量 |
| `grade.pass_score` | 0.5 | 最高分达到该值才算检索成功 |
| `grade.max_retries` | 2 | 最多改写重试次数 |

## 4. 混合检索

### 4.1 单条查询（草稿，pymilvus 2.5.x）

```python
from pymilvus import AnnSearchRequest, WeightedRanker

LIGHT_FIELDS = ["chunk_id", "doc_id", "version", "type"]

def hybrid_one(client, coll: str, query: str, qvec: list[float],
               expr: str, cfg) -> list[dict]:
    dense = AnnSearchRequest(
        data=[qvec], anns_field="dense",
        param={"metric_type": "COSINE", "params": {"search_list": cfg.search_list}},
        limit=cfg.dense_top_k, expr=expr)
    sparse = AnnSearchRequest(
        data=[query], anns_field="sparse",          # BM25：直接传原始查询文本
        param={"metric_type": "BM25"},
        limit=cfg.sparse_top_k, expr=expr)
    res = client.hybrid_search(
        coll, reqs=[dense, sparse],
        ranker=WeightedRanker(cfg.w_dense, cfg.w_sparse),
        limit=cfg.per_query_limit, output_fields=LIGHT_FIELDS)
    return [{**h["entity"], "score": h["distance"]} for h in res[0]]
```

- WeightedRanker 会先把两路分数归一化再加权，具体的归一化方式以所用 Milvus 版本为准。
- 第一轮只取轻量字段，避免从 mmap 的文本字段里读 150 行大文本；合并后只对前 30 个回表。
- 多条查询用线程池并发执行（pymilvus 是同步接口）。

### 4.2 过滤条件

```python
import re

DOC_ID_RE = re.compile(r"^[0-9a-f]{16}$")
FILE_TYPES = {"pdf", "doc", "docx", "ppt", "pptx", "png", "jpg", "jpeg", "md", "txt"}

def build_expr(filters: dict | None) -> str:
    parts = ["searchable == true"]
    if not filters:
        return parts[0]
    if ft := filters.get("file_types"):
        if not set(ft) <= FILE_TYPES:            # 白名单，防止表达式注入
            raise ValueError(f"不支持的文件类型: {set(ft) - FILE_TYPES}")
        parts.append("file_type in [" + ",".join(f'"{t}"' for t in sorted(ft)) + "]")
    if ids := filters.get("doc_ids"):
        if len(ids) > 100 or not all(DOC_ID_RE.fullmatch(i) for i in ids):
            raise ValueError("非法 doc_id")
        parts.append("doc_id in [" + ",".join(f'"{i}"' for i in ids) + "]")
    return " and ".join(parts)
```

用户输入只能通过白名单或正则校验后拼进表达式，不接受任意字符串。

### 4.3 多查询合并

```python
def merge(results: list[list[dict]], limit: int) -> list[dict]:
    best: dict[str, dict] = {}
    for hits in results:
        for h in hits:
            if h["chunk_id"] not in best or h["score"] > best[h["chunk_id"]]["score"]:
                best[h["chunk_id"]] = h
    # 增量入库的短暂窗口内，同一文档可能新旧版本并存：只留最新版本
    latest: dict[str, int] = {}
    for h in best.values():
        latest[h["doc_id"]] = max(latest.get(h["doc_id"], 0), h["version"])
    hits = [h for h in best.values() if h["version"] == latest[h["doc_id"]]]
    return sorted(hits, key=lambda h: h["score"], reverse=True)[:limit]
```

所有查询用同一套权重，分数可以直接比较，同一个 chunk 被多条查询命中时取最高分。

### 4.4 召回后去重

回表取回完整字段后，按 `content_hash` 去重，保留分数最高的副本：

```python
def dedup_by_content(hits: list[dict]) -> list[dict]:
    """跨文档重复内容只保留分数最高的一份。"""
    best: dict[str, dict] = {}
    for h in hits:
        hash_key = h["content_hash"]
        if hash_key not in best or h["score"] > best[hash_key]["score"]:
            best[hash_key] = h
    return list(best.values())
```

- 入库时跨文档副本都标记 `searchable=true`（见[文档切分](文档切分.md) §11），这样限定文档检索不会丢内容。
- 召回后按内容去重，避免多个副本占用重排名额和 token 预算。
- `content_hash` 是 `text` 归一化后的 sha256，在切分阶段计算并写入 Milvus（[文档切分](文档切分.md) §11）。

### 4.5 数据结构

回表之后每个候选都是一个完整的 `Hit`；扩展取回的内容不重排，用 `Expansion` 表示。两者都从[向量化建库](向量化建库.md) §5.1 的 `ChunkFields` 派生，字段和 Milvus 一致，只是不带向量。代码在 `src/ragagent/retrieval/models.py`。

```python
from typing import Literal
from pydantic import BaseModel, Field

class Hit(ChunkFields):
    score: float                        # 融合分数（WeightedRanker），多查询取最高
    rerank_score: float | None = None   # 重排后填；重排降级时保持 None

ExpansionRole = Literal["section", "neighbor", "lead_in", "split_sibling", "attachment", "anchor"]

class Expansion(ChunkFields):
    role: ExpansionRole                 # 取值见 §6

class RetrievalResult(BaseModel):
    """RAGState.retrieval 的结构。"""
    top_score: float = 0.0              # 重排最高分，被 per_doc_cap 挡掉的也算；没有候选时为 0
    degraded: bool = False              # 重排超时或报错（§8），grade 直接放行
    dense_only: bool = False            # hybrid_search 失败后只查了稠密向量（§8）
    timings_ms: dict[str, int] = Field(default_factory=dict)   # embed / hybrid / fetch / rerank / expand
```

- `RAGState` 里的 `candidates`、`hits`、`expansions`、`retrieval` 存的是 `model_dump()` 之后的 dict，checkpointer 直接序列化；节点内部用模型校验。
- `expansions` 的 key 是命中的 `chunk_id`，value 是 `list[Expansion]` 的 dict 形式。

## 5. 重排

### 5.1 模型与服务

| 项 | 值 |
|----|----|
| 模型 | BAAI/bge-reranker-v2-m3，fp16，RTX 4060 |
| 部署 | 放进编码服务，新增 `POST /rerank`：`{"query": ..., "passages": [...]}` → `{"scores": [...]}`；后处理的支持度校验用 `POST /rerank/pairs`：`{"pairs": [[query, passage], ...]}` → `{"scores": [...]}` |
| 调用 | FlagEmbedding 的 `FlagReranker.compute_score(pairs, normalize=True)`，输出经过 sigmoid，范围 0~1 |
| 输入 | `(standalone_question, embed_text)`：带标题路径，截断到 `max_length=512` |
| 批量 | 30 对一次调用 |

- 用 `standalone_question` 而不是每条改写查询：改写只是为了召回，相关性以用户真正的问题为准。
- 文本和图片在同一个列表里一起排：图片 chunk 的 `embed_text` 是“标题路径 + 图片说明 + 前后段落”。重排模型只看文字，所以没有说明文字的图片基本会被排掉，这是已接受的取舍。

### 5.2 筛选

```python
def select(hits: list[dict], scores: list[float], cfg) -> list[dict]:
    for h, s in zip(hits, scores):
        h["rerank_score"] = s
    ranked = sorted(hits, key=lambda h: h["rerank_score"], reverse=True)
    out, per_doc = [], {}
    for h in ranked:
        if h["rerank_score"] < cfg.threshold:
            break
        if per_doc.get(h["doc_id"], 0) >= cfg.per_doc_cap:
            continue
        per_doc[h["doc_id"]] = per_doc.get(h["doc_id"], 0) + 1
        out.append(h)
        if len(out) == cfg.top_n:
            break
    return out
```

`top_score` 取重排后的最高分（即使它被 per_doc_cap 挡掉也算），给 grade 用。

## 6. 上下文扩展

检索阶段只负责把扩展内容取回来；用哪些、怎么排、怎么按 token 预算截断，由[上下文构造](上下文构造.md)决定。

| 命中 chunk | 取回内容 | role |
|------------|----------|------|
| text / code，所在节 `section_tokens ≤ 1500` 且命中本身不是整节 | 整节的全部 text / code chunk（含 `searchable=false` 的） | `section` |
| text / code，所在节超过 1500 | `prev_id`、`next_id` | `neighbor` |
| code | `related_ids` 里的引导段落 | `lead_in` |
| 递归拆分出来的段（`meta.split_part`） | 紧挨着的前后拆分段（同一组内的 prev / next） | `split_sibling` |
| 有 `image_ids` 的 text | 关联图片，每个 chunk 最多 2 张，全部最多 4 张；只做展示附件，不占 top 8 名额 | `attachment` |
| image | `meta.anchor_id` 指向的锚点 chunk | `anchor` |

- 按 id 取的内容（neighbor、lead_in、split_sibling、attachment、anchor）汇总去重后，一次 `client.query(filter='chunk_id in [...]')` 取回（最多约 40 个）。
- 整节按 `(doc_id, version, section_idx)` 一次批量取回：多个节用 `or` 拼成一个表达式，`limit=200`，并排除 `type == "image"`。这三个值都来自库里的字段（doc_id 过正则校验、另外两个是整数），不来自用户输入。
- 整节阈值取 `config.yaml` 的 `expansion.section_max_tokens`，上下文构造用同一个值。
- 扩展内容不重排，也不受分数阈值限制，但会去掉已经在 `hits` 里的。取回来的内容不一定全部用上，由上下文构造按预算挑选。

## 7. Grade 与重试

只用重排分数判断，不额外调用 LLM：

| 条件 | 去向 |
|------|------|
| `top_score ≥ 0.5` | `build_context` |
| `top_score < 0.5` 且 `retry_count < 2` | `rewrite`：用了软过滤就先去掉它；否则调用改写模型生成新查询，见[用户问题预处理](用户问题预处理.md) §9 |
| `top_score < 0.5` 且已重试 2 次 | `fallback`：回答“资料不足”，并列出最接近的几个来源供用户参考 |
| 重排服务降级（§8） | 直接 `build_context`，分数不可信，不做重试判断 |

- 已知局限：重排分数只能说明内容相关，不能说明信息足以回答问题。回答中信息不全的情况交给[后处理](后处理.md)检查。
- 0.5 是初始值，按 §10 的方法在评测集上校准。

LangGraph 里 grade 做成条件边，不单独占一个节点：

```python
def route_after_rerank(state: RAGState) -> str:
    if state["retrieval"].get("degraded"):
        return "build_context"
    if state["retrieval"]["top_score"] >= cfg.grade.pass_score:
        return "build_context"
    if state["retry_count"] < cfg.grade.max_retries:
        return "rewrite"
    return "fallback"

g.add_edge("retrieve", "rerank")
g.add_conditional_edges("rerank", route_after_rerank,
                        ["build_context", "rewrite", "fallback"])
# rewrite → retrieve / fallback 的条件边见 用户问题预处理.md §13
```

## 8. 降级

| 故障 | 处理 |
|------|------|
| 重排超时（> 2 秒）或报错 | 用融合分数的顺序取 top 8，`degraded=true`，不做 grade 重试 |
| hybrid_search 超时或报错 | 重试一次只查稠密向量；还失败就返回错误 |
| 编码服务不可用 | 无法检索，接口返回 503 |
| 某条改写查询失败 | 忽略这一条，用其余查询的结果 |

降级情况都记日志并计数，接入[评估与监控](评估与监控.md)的告警。

## 9. 延迟预算（4060，未实测）

| 步骤 | 估算 |
|------|------|
| 查询编码（1~3 条） | 20~50 ms |
| hybrid_search（并发） | 50~200 ms，BM25 走 mmap 时波动较大 |
| 合并 + 回表 | 20~50 ms |
| 重排 30 对 | 600~1000 ms |
| 上下文扩展查询 | 20~50 ms |
| 合计 | p95 目标 ≤ 1.5 s |

每重试一次，大约再加一轮检索和重排的时间；如果调用了改写 LLM，再加 0.5~1 秒。算上预处理，最坏情况（重试 2 次）约 5~6 秒。

## 10. 评测与调参

评测集和指标的整体设计放在[评估与监控](评估与监控.md)，这里只列检索阶段要调的东西：

| 调什么 | 怎么调 | 看什么 |
|--------|--------|--------|
| 融合权重 | 稠密权重取 0.5 / 0.6 / 0.7 / 0.8 | 合并后前 30 的 Recall@30 |
| 关键词类查询 | 单独统计错误码、函数名、型号这类查询 | 权重偏向稠密时这类查询是否明显变差；变差就考虑按查询类型调权重 |
| 候选数 | 20 / 30 / 50 | 重排后 Recall@8 和重排耗时 |
| `search_list` | 64 / 100 / 160 | ANN 召回和检索延迟 |
| 重排阈值 0.3 | 看被阈值丢掉的 chunk 里有多少是标注为相关的 | 误丢率 |
| grade 通过线 0.5 | 分别画出“能回答”和“不能回答”两类问题的 top_score 分布，取两者分得最开的位置 | 误拒率 / 误放率 |
| 图片 | 单独统计答案在图片里的问题 | 图片 chunk 进入 top 8 的比例 |

指标：Recall@30（重排前）、Recall@8 / MRR / nDCG@8（重排后）、p50 / p95 延迟、重试率、fallback 率、降级率。

## 13. 待讨论

- 融合权重固定为一套，关键词类查询可能吃亏；评测后如果差距明显，再考虑按查询类型切换权重（由预处理阶段判断查询类型）。
- 没有说明文字的图片基本进不了结果；如果评测显示图片问题召回差，可以回头在清洗阶段打开多模态 LLM 生成图片描述。
- 重排延迟需要在 4060 上实测，超出预算时优先把候选数降到 20 或 `max_length` 降到 384。
