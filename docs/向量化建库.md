# 向量化建库

## 1. 目标

把[文档切分](文档切分.md)输出的 chunk 向量化后写入 Milvus：
- 每个 chunk 带上自己所在的标题路径一起向量化（`embed_text`）。
- 稠密向量：Visualized-BGE（bge-m3 底座），文本 chunk 和图片 chunk 编码到同一个 1024 维空间，建 DISKANN 索引。
- 稀疏向量：Milvus 内置 BM25，基于同一份 `embed_text` 自动生成，负责关键词匹配。
- 标量字段：文档、章节、页码、图片关联等元数据，用于过滤、引用和上下文扩展。

- 输入：`data/chunks/{doc_id}/v{version}.jsonl`
- 输出：Milvus collection `rag_chunks`（通过别名访问），登记表状态更新为 `indexed`

参数分两处：应用侧参数（模型、batch、连接信息）在项目根目录 `config.yaml` 的 `index`、`services` 段；Milvus 服务端参数（DISKANN 构建参数、mmap）只能写在 Milvus 自己的 `milvus.yaml` 里，见 §6。

## 2. 流程

```
读取 chunk jsonl
  ↓ 按类型分组：text / code 走文本编码，image 走图文联合编码
  ↓ 分批送入 Visualized-BGE → 1024 维稠密向量（L2 归一化）
  ↓ 组装行数据（BM25 稀疏向量由 Milvus Function 在写入时自动生成）
  ↓ 批量 insert 新版本 → 删除同一 doc_id 的旧版本 → flush
  ↓ 更新登记表：status=indexed、chunk 数、模型版本
```

## 3. 向量化输入：标题路径

格式（切分阶段生成，这里直接使用）：

```
{文档标题} > {一级标题} > {二级标题} > ...
{代码 chunk 的引导句 / 拆分段的 (续 i/n)}
{text}
```

例子：

| chunk 类型 | embed_text |
|------------|------------|
| 普通文本 | `部署手册 > 第2章 部署 > 2.3 配置`<br>`配置文件默认位于 /etc/app/config.yaml，启动时按以下顺序加载……` |
| 代码 | `部署手册 > 第2章 部署 > 2.3 配置`<br>`修改端口可以使用下面的配置：`<br>`（yaml 代码块原文）` |
| 拆分段 | `部署手册 > 第3章 运维 > 3.1 日志`<br>`(续 2/3)`<br>`……` |
| 图片 | 图片 + `部署手册 > 第1章 架构`<br>`图1-2 系统整体架构图`<br>`{图片前后的段落摘要}` |

- 查询端不加任何前缀或指令，直接编码用户问题（bge-m3 系列不需要 query instruction）。
- 标题路径的截断规则见[文档切分](文档切分.md) §9.4。
- `embed_text` 超过模型最大长度时，从正文末尾截断，标题路径始终保留。

## 4. Embedding 模型

### 4.1 模型

| 项 | 值 |
|----|----|
| 模型 | Visualized-BGE，bge-m3 底座（权重 `Visualized_m3.pth`，来自 HuggingFace `BAAI/bge-visualized`） |
| 代码 | FlagEmbedding 仓库的 `research/visual_bge` |
| 维度 | 1024 |
| 相似度 | 输出已做 L2 归一化，Milvus 用 `COSINE` |
| 文本编码 | `model.encode(text=...)` |
| 图文编码 | `model.encode(image=path, text=...)` |
| 部署 | 本地 RTX 4060（8 GB 显存），fp16 |

> 权重名、安装方式和最大文本长度是我根据目前了解写的，没有实测。落地前要确认两件事：
> 1. 文本输入的最大长度：决定切分阶段的 `max_tokens` 是否需要调小。
> 2. 是否支持批量编码：官方示例是逐条调用，批量可能要直接调用内部的 `encode_text` / `encode_mm`。

### 4.2 编码服务

入库、在线查询和语义断点计算都要用同一个模型。把模型封装成一个内部 HTTP 服务，GPU 上只加载一份：

| 接口 | 输入 | 输出 |
|------|------|------|
| `POST /embed/text` | `{"texts": [...]}` | `{"vectors": [[...], ...]}` |
| `POST /embed/image` | `{"items": [{"image_path": ..., "text": ...}]}` | `{"vectors": [...]}` |
| `GET /health` | | 模型名、版本、设备 |

请求和响应结构（`src/ragagent/index/models.py`，编码服务和测试桩共用）：

```python
from pathlib import PurePosixPath
from pydantic import BaseModel, field_validator

class EmbedItem(BaseModel):
    image_path: str
    text: str

    @field_validator("image_path")
    @classmethod
    def _relative(cls, v: str) -> str:
        p = PurePosixPath(v)
        if not v or p.is_absolute() or ".." in p.parts:
            raise ValueError(f"image_path 必须是相对路径且不含 ..: {v!r}")
        return v

class EmbedTextRequest(BaseModel):
    texts: list[str]

class EmbedImageRequest(BaseModel):
    items: list[EmbedItem]

class EmbedResponse(BaseModel):
    vectors: list[list[float]]
```

- 只监听 `127.0.0.1` 或内网地址，默认没有鉴权，不要暴露到公网；需要跨机器访问时加 token 鉴权。
- `image_path` 只允许 `data/clean/` 下的相对路径，拒绝 `..` 和绝对路径，防止读取任意文件。`EmbedItem` 在反序列化时先挡一次，服务端解析成绝对路径后再确认仍在 `data/clean/` 下。
- 单进程串行推理，外面按 batch 聚合请求。
- Rerank 模型（bge-reranker-v2-m3）以后也可以放在这个服务里。

### 4.3 编码封装（草稿）

```python
import torch
from visual_bge.modeling import Visualized_BGE

class Embedder:
    def __init__(self, weight: str, device: str = "cuda"):
        self.model = Visualized_BGE(model_name_bge="BAAI/bge-m3",
                                    model_weight=weight)
        self.model.eval()
        self.version = "visualized-bge-m3@" + weight.rsplit("/", 1)[-1]

    @torch.no_grad()
    def text(self, texts: list[str]) -> list[list[float]]:
        return [self.model.encode(text=t).squeeze(0).float().cpu().tolist()
                for t in texts]

    @torch.no_grad()
    def image(self, items: list[tuple[str, str]]) -> list[list[float]]:
        return [self.model.encode(image=p, text=t).squeeze(0).float().cpu().tolist()
                for p, t in items]
```

先按逐条调用实现，确认可以批量编码后再改成批量调用。

## 5. Milvus Collection 设计

### 5.1 字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `chunk_id` | VARCHAR(64)，主键 | `{doc_id}:v{version}:{seq:05d}`，由切分阶段生成 |
| `doc_id` | VARCHAR(32) | 按文档删除和过滤 |
| `version` | INT32 | 文档版本，删除旧版本时使用 |
| `seq` | INT32 | 文档内顺序 |
| `tokens` | INT32 | chunk 正文的 token 数，上下文构造算预算用 |
| `section_idx` | INT32 | 所在节在文档内的编号，整节取回用 |
| `section_tokens` | INT32 | 所在节的总 token 数，决定能否整节放入上下文 |
| `type` | VARCHAR(16) | `text` / `code` / `image` |
| `text` | VARCHAR(65535) | 原文，给 LLM 和前端展示；不参与检索 |
| `embed_text` | VARCHAR(65535)，开启中文分词器 | 标题路径 + 正文，BM25 的输入 |
| `content_hash` | VARCHAR(64) | `text` 归一化后的 sha256（[文档切分](文档切分.md) §11），召回后去重用；不建索引 |
| `dense` | FLOAT_VECTOR(1024) | Visualized-BGE 向量 |
| `sparse` | SPARSE_FLOAT_VECTOR | BM25 Function 自动生成，写入时不用提供 |
| `title` | VARCHAR(512) | 文档标题 |
| `section_path` | VARCHAR(2048) | 用 ` > ` 连接的标题路径，展示和引用用 |
| `source_path` | VARCHAR(1024) | 原文件路径 |
| `file_type` | VARCHAR(16) | pdf / docx / pptx / png / md / txt |
| `page_start` / `page_end` | INT32 | 没有页码时为 -1 |
| `image_path` | VARCHAR(1024) | 只有 image chunk 有值，其余为空字符串 |
| `prev_id` / `next_id` | VARCHAR(64) | 上下文扩展用，没有时为空字符串 |
| `image_ids` | ARRAY<VARCHAR(64)>，最多 32 个 | 本 chunk 关联的图片 |
| `related_ids` | ARRAY<VARCHAR(64)>，最多 32 个 | 代码与引导段落、图片与附近文本 |
| `searchable` | BOOL | 重复或模板文本为 false，检索时过滤掉，但保留在库里供上下文扩展 |
| `meta` | JSON | strategy、split_part、lang、anchor_id 等 |

- 所有标量字段都给默认值（空字符串或 -1），避免依赖 nullable 特性，兼容性更好。
- VARCHAR 的长度按字节计算。800 token 的中文 chunk 大约 3~4 KB，离 65535 的上限很远。
- 不做部门、密级等权限过滤，collection 里不加权限字段；访问控制只靠 Milvus 账号鉴权（§9）。

对应的模型（`src/ragagent/index/models.py`）。`ChunkFields` 是除向量外的全部字段，[检索与重排](检索与重排.md) §4.5 的 `Hit` 也从它派生：

```python
from pydantic import ConfigDict

class ChunkFields(BaseModel):
    model_config = ConfigDict(extra="forbid")   # 字段名拼错直接报错，不静默丢弃

    chunk_id: str
    doc_id: str
    version: int
    seq: int
    tokens: int
    section_idx: int
    section_tokens: int
    type: str
    text: str
    embed_text: str
    content_hash: str
    title: str
    section_path: str           # " > " 连接
    source_path: str
    file_type: str
    page_start: int             # 没有页码时 -1
    page_end: int
    image_path: str             # 非 image chunk 为 ""
    prev_id: str                # 没有时为 ""
    next_id: str
    image_ids: list[str]
    related_ids: list[str]
    searchable: bool
    meta: dict

class ChunkRow(ChunkFields):
    """写入 Milvus 的一行；sparse 由 BM25 Function 生成，不在这里。"""
    dense: list[float]

def to_row(c: Chunk, doc: CleanDocument, dense: list[float]) -> dict:
    none_to = {"page_start": -1, "page_end": -1, "image_path": "", "prev_id": "", "next_id": ""}
    base = c.model_dump(exclude={"section_path", *none_to})
    fixed = {k: d if getattr(c, k) is None else getattr(c, k) for k, d in none_to.items()}
    return ChunkRow(**base, **fixed, dense=dense, title=doc.title,
                    source_path=doc.source_path, file_type=doc.file_type,
                    section_path=" > ".join(c.section_path)).model_dump()
```

### 5.2 建表代码（草稿，pymilvus 2.5.x）

```python
from pymilvus import MilvusClient, DataType, Function, FunctionType

def create_collection(client: MilvusClient, name: str, dim: int) -> None:
    """dim 取 index.dim。"""
    s = client.create_schema(auto_id=False, enable_dynamic_field=False)
    s.add_field("chunk_id", DataType.VARCHAR, max_length=64, is_primary=True)
    s.add_field("doc_id", DataType.VARCHAR, max_length=32)
    s.add_field("version", DataType.INT32)
    s.add_field("seq", DataType.INT32)
    s.add_field("tokens", DataType.INT32)
    s.add_field("section_idx", DataType.INT32)
    s.add_field("section_tokens", DataType.INT32)
    s.add_field("type", DataType.VARCHAR, max_length=16)
    s.add_field("text", DataType.VARCHAR, max_length=65535)
    s.add_field("embed_text", DataType.VARCHAR, max_length=65535,
                enable_analyzer=True, analyzer_params={"type": "chinese"})
    s.add_field("content_hash", DataType.VARCHAR, max_length=64)
    s.add_field("dense", DataType.FLOAT_VECTOR, dim=dim)
    s.add_field("sparse", DataType.SPARSE_FLOAT_VECTOR)
    s.add_field("title", DataType.VARCHAR, max_length=512)
    s.add_field("section_path", DataType.VARCHAR, max_length=2048)
    s.add_field("source_path", DataType.VARCHAR, max_length=1024)
    s.add_field("file_type", DataType.VARCHAR, max_length=16)
    s.add_field("page_start", DataType.INT32)
    s.add_field("page_end", DataType.INT32)
    s.add_field("image_path", DataType.VARCHAR, max_length=1024)
    s.add_field("prev_id", DataType.VARCHAR, max_length=64)
    s.add_field("next_id", DataType.VARCHAR, max_length=64)
    s.add_field("image_ids", DataType.ARRAY, element_type=DataType.VARCHAR,
                max_capacity=32, max_length=64)
    s.add_field("related_ids", DataType.ARRAY, element_type=DataType.VARCHAR,
                max_capacity=32, max_length=64)
    s.add_field("searchable", DataType.BOOL)
    s.add_field("meta", DataType.JSON)

    # BM25：embed_text 分词后自动生成 sparse，写入时不需要提供
    s.add_function(Function(name="bm25", function_type=FunctionType.BM25,
                            input_field_names=["embed_text"],
                            output_field_names=["sparse"]))

    idx = client.prepare_index_params()
    idx.add_index("dense", index_type="DISKANN", metric_type="COSINE")
    idx.add_index("sparse", index_type="SPARSE_INVERTED_INDEX", metric_type="BM25")
    idx.add_index("doc_id", index_type="INVERTED")
    idx.add_index("type", index_type="BITMAP")
    idx.add_index("file_type", index_type="BITMAP")
    idx.add_index("searchable", index_type="BITMAP")
    client.create_collection(name, schema=s, index_params=idx)
```

## 6. 索引

### 6.1 DISKANN（稠密向量）

DISKANN 只对已封存（sealed）的 segment 生效；刚写入、还在增长的 segment 用临时索引或暴力检索，所以新数据写入后马上就能查到，只是那部分会慢一些。

构建参数在 `milvus.yaml` 里全局配置：

```yaml
queryNode:
  enableDisk: true            # 必须打开，否则无法加载 DISKANN
common:
  DiskIndex:
    MaxDegree: 56             # 图的出度：越大召回越高，索引越大、构建越慢
    SearchListSize: 100       # 构建时的候选列表长度
    PQCodeBudgetGBRatio: 0.0625  # 常驻内存的 PQ 压缩向量占原始向量的比例（默认 0.125，为满足 10 GB 预算减半）
    SearchCacheBudgetGBRatio: 0.02 # 缓存图上热点节点的内存比例（默认 0.1，同上）
    BeamWidthRatio: 4.0       # 每次磁盘 IO 的并行度
```

- 两个内存比例按 1000 万 chunk、Milvus 常驻内存 10 GB 以内来定，见 §6.4。
- PQ 只用来在图上导航，最终距离用磁盘上的原始向量重新计算，所以 PQ 比例减半对召回的影响有限；需要用 §10 的 ANN 召回测试确认。
- 检索参数 `search_list`（要求不小于 top_k，默认 100）在[检索与重排](检索与重排.md)里调。
- 参数名以所用 Milvus 版本的文档为准。

### 6.2 BM25（稀疏向量）

- 分词器：`{"type": "chinese"}`（jieba 分词，中英文混排都能处理）。
- 输入是 `embed_text`，标题里的词也能被关键词检索命中，比如搜“2.3 配置”。
- 代码 chunk 里的标识符（`max_tokens`、`getUserName`）可能被切碎，需要用样例验证；效果不好的话再换成自定义 analyzer（例如加上保留下划线的规则）。
- BM25 的 IDF 统计由 Milvus 维护，增删数据后自动更新。

### 6.3 标量索引

| 字段 | 索引 | 用途 |
|------|------|------|
| `doc_id` | INVERTED | 按文档删除、过滤 |
| `type` | BITMAP | 只查文本 / 只查图片 |
| `file_type` | BITMAP | 按文件类型过滤 |
| `searchable` | BITMAP | 检索时固定加 `searchable == true` |

### 6.4 资源估算

按 1000 万 chunk、平均 350 token/chunk 估算。原始向量 = 1000 万 × 1024 × 4 字节 ≈ 41 GB。

目标：Milvus 常驻内存 ≤ 10 GB。做法是向量只在内存里留 PQ 压缩码，其余数据（原始向量、文本、稀疏索引）全部走 mmap 或磁盘。

内存预算：

| 项 | 估算 | 说明 |
|----|------|------|
| DISKANN PQ 码 | 2.6 GB | 41 GB × 0.0625 |
| DISKANN 节点缓存 | 0.8 GB | 41 GB × 0.02 |
| 主键与删除过滤（bloom filter 等） | 0.5~1 GB | VARCHAR 主键约 26 字节 × 1000 万 |
| 标量索引（doc_id / type / file_type / searchable） | 约 0.3 GB | |
| 标量原始字段、文本字段 | 很少 | 打开 mmap，只占页缓存 |
| BM25 稀疏倒排索引 | 很少（前提是支持 mmap） | 不 mmap 的话约 10~12 GB，会直接超预算 |
| Milvus 进程本身 + 增长中的 segment | 1.5~2.5 GB | |
| 合计 | 约 6~7.5 GB | 留 2~3 GB 余量给查询峰值 |

mmap 配置（`milvus.yaml`，字段名以实际版本为准）：

```yaml
queryNode:
  mmap:
    scalarField: true    # text、embed_text、meta 等
    scalarIndex: true
    vectorField: true    # dense 原始数据、sparse 原始数据
    vectorIndex: true    # sparse 倒排索引（DISKANN 本身已在磁盘上）
```

最大风险是 BM25：需要确认所用版本的 SPARSE_INVERTED_INDEX 能否 mmap。如果不能，按顺序备选：
1. 分词时去掉停用词、只保留中文词和标识符，缩小倒排表，再测一次内存；
2. BM25 移到外部引擎（Elasticsearch / OpenSearch），Milvus 只做稠密检索，在应用层融合。

磁盘占用：

| 项 | 估算 | 说明 |
|----|------|------|
| DISKANN 索引 | 约 82 GB | 每个节点 = 4096 字节向量 + 邻接表，超过一个 4 KB 扇区，占 2 个扇区（8 KB） |
| 稠密向量原始数据 | 约 41 GB | |
| 文本和标量字段 | 约 35~40 GB | text + embed_text 每个 chunk 约 3 KB |
| BM25 稀疏向量与索引 | 约 25 GB | |
| 合计 | 约 190 GB | |
| 重建期间新旧两份 | 约 380 GB | 见 §8 |

- 建议 1 TB NVMe SSD。DISKANN 每跳读 8 KB，随机读 IOPS 直接决定检索延迟，不要用 SATA 盘或机械盘。
- 可选优化：如果所用版本的 DISKANN 支持 FLOAT16 向量，每个节点能放进一个扇区，索引大小和 IO 都减半。改动是把 `dense` 改成 `FLOAT16_VECTOR`，需要验证召回后再决定。
- 构建峰值：DISKANN 按 segment 构建，每次构建会临时占用几 GB 内存。把索引构建并发限制为 1，首次全量入库时监控内存，超出预算就把 segment 上限调小（例如 1 GB）。
- 主机内存：Milvus ≤ 10 GB + 编码服务约 3 GB + 系统，再加上 mmap 需要的页缓存，建议 32 GB。

### 6.5 GPU（RTX 4060，8 GB）

| 项 | 显存 |
|----|------|
| Visualized-BGE（m3）fp16 权重 | 约 1.5 GB |
| bge-reranker-v2-m3 fp16 权重 | 约 1.1 GB |
| 推理激活（batch 32 × 512 token） | 1~2 GB |

两个模型可以同时常驻。批量入库时不需要加载 reranker，把显存让给更大的 batch。

入库速度（未实测，需要跑基准确认）：
- 文本 chunk 按长度排序后分批，减少 padding；fp16 下大约 50~100 chunk/s。
- 1000 万 chunk 全量编码大约需要 1.5~3 天。所以全量重建成本很高，平时以增量入库为主；重建通过别名切换进行（§8），不影响在线服务。
- 如果 MinerU 也自部署在这张卡上，解析和编码要错开时间，不要同时跑。

## 7. 增量写入

按文档为单位处理，和登记表的 `version` 对应：

| 登记表变化 | 处理 |
|------------|------|
| 新文档 | 写入全部 chunk |
| 内容变化（version + 1） | 写入新版本 → 删除同一 doc_id 下 version 更小的 chunk |
| 文件删除 | 按 doc_id 删除全部 chunk |
| 解析失败 / 空文档 / 重复文档 | 不写入 |

先写新版本再删旧版本：中间短时间内新旧版本同时存在，但不会出现这个文档完全查不到的空窗期。检索时按 `doc_id` 去重，可以兜住这个短暂的重复。

```python
import re

DOC_ID_RE = re.compile(r"^[0-9a-f]{16}$")

def index_document(client, coll: str, emb: Embedder,
                   doc: CleanDocument, chunks: list[Chunk]) -> int:
    doc_id, version = doc.doc_id, doc.version
    if not DOC_ID_RE.fullmatch(doc_id):     # doc_id 会拼进过滤表达式，先校验
        raise ValueError(f"非法 doc_id: {doc_id}")
    rows = []
    for batch in batched(chunks, 32):
        texts = [c for c in batch if c.type != "image"]
        images = [c for c in batch if c.type == "image"]
        vecs = dict(zip([c.chunk_id for c in texts],
                        emb.text([c.embed_text for c in texts])))
        vecs.update(zip([c.chunk_id for c in images],
                        emb.image([(c.image_path, c.embed_text) for c in images])))
        rows += [to_row(c, doc, vecs[c.chunk_id]) for c in batch]
    for batch in batched(rows, 500):
        client.upsert(coll, batch)          # chunk_id 是确定性的，重试时幂等
    client.delete(coll, filter=f'doc_id == "{doc_id}" and version < {version}')
    return len(rows)
```

- 用 upsert 而不是 insert：中途失败重跑时不会产生重复行。
- 整批文档处理完调用一次 `flush`，不要每个文档都 flush，否则会产生大量小 segment。
- 登记表在写入成功后才改成 `indexed`，并记录 `chunk_count` 和 `embed_model`（`Embedder.version`）。
- 删除文档（`deleted`）时只执行 `delete(filter='doc_id == "..."')`。

## 8. 模型升级与重建

换 Embedding 模型、改 `embed_text` 格式或改切分参数后，旧向量就不能用了，需要全量重建：

1. 新建 collection `rag_chunks_v{n+1}`，全量写入。
2. 在新 collection 上跑 §10 的验证和评测集。
3. 通过后执行 `client.alter_alias(collection_name="rag_chunks_v{n+1}", alias="rag_chunks")`，在线服务无感切换。
4. 旧 collection 保留几天，方便回滚，之后再删除。

在线服务只通过别名 `rag_chunks` 访问，不写死 collection 名。入库脚本平时也写别名；重建时显式指定新 collection，重建期间的增量更新两边都要写，或者先暂停增量入库。

## 9. 部署

- Milvus Standalone，用 docker compose 部署，镜像版本固定到某个 2.5.x 补丁版本，不用 `latest`。
- `milvus.yaml` 打开 `queryNode.enableDisk: true`；数据目录（本地存储和 DISKANN 文件）挂到 NVMe SSD 上。
- 安全：
  - 打开 `common.security.authorizationEnabled: true`，修改默认的 root 密码，另建一个只读用户给在线服务、一个读写用户给入库脚本。
  - 19530 端口只对内网开放；可视化管理工具 Attu 按需部署，同样不暴露到公网。
  - 连接信息（地址、用户名、密码）放在环境变量里，不写进配置文件或代码。
- 编码服务和 Milvus 部署在同一台机器或同一个内网里。
- 内存：`milvus.yaml` 按 §6.4 打开 mmap；docker compose 给 Milvus 容器设 `mem_limit: 12g` 作为兜底（比 10 GB 目标略宽，页缓存在内存紧张时会被回收）。用 Prometheus 监控常驻内存（RSS），超过 10 GB 就告警。
- 索引构建并发限制为 1，避免多个 DISKANN 同时构建导致内存峰值叠加。

## 10. 验证

| 检查项 | 方法 | 通过标准 |
|--------|------|----------|
| 写入数量 | jsonl 中的 chunk 数和 Milvus 中按 doc_id 统计的数量对比 | 完全一致 |
| 自检索 | 随机抽 50 个 chunk，用它自己的向量查询 | top1 是它自己 |
| ANN 召回 | 抽 1000 条查询，DISKANN 的结果和暴力检索（FLAT）的结果对比 | Recall@10 ≥ 0.95 |
| BM25 | 用只出现在个别 chunk 里的词（错误码、函数名）查询 | 目标 chunk 在 top5 里 |
| 标题路径 | 用章节标题的说法提问（例如“部署章节里的配置文件在哪”） | 命中对应章节的 chunk |
| 图片 | 用描述图片内容的文字查询 | 对应的 image chunk 在 top10 里 |
| 增量 | 修改一个文档重新入库 | 旧版本 chunk 全部删除，没有重复 |

ANN 召回不达标时，按顺序调整：检索时的 `search_list` → `MaxDegree`（只增加磁盘和构建时间）→ `PQCodeBudgetGBRatio`（会增加内存，受 10 GB 预算限制，最后才动）。
