# 用户问题预处理

## 1. 目标

把用户的原始问题整理成检索能直接用的输入：
- 判断意图：知识问答（rag）走检索，闲聊（chat）直接回答，问题太模糊（clarify）先反问用户。
- 指代消解：结合对话历史把问题补全，重排使用补全后的完整问题。
- 查询扩展：在完整问题之外，最多再生成 2 条同义改写或拆分出的子问题。
- 范围识别：从问题里识别用户想限定的文档或文件类型，作为软过滤条件使用。
- 重试改写：grade 没通过时，换一种查询方式重新检索。

前四项放在同一次 LLM 调用里完成，重试改写单独调用一次。

输入：
- 接口请求：`POST /api/chat` 的 `question`、可选 `session_id`、可选 `filters`（硬过滤）；会话也可由 `X-Session-ID` 提供，同传必须一致且不能为空。
- 会话状态：LangGraph checkpointer 按 `session_id` 保存的对话历史

输出（写入 RAGState）：

| 字段 | 说明 |
|------|------|
| `intent` | `rag` / `chat` / `clarify` |
| `standalone_question` | 补全后的完整问题，重排用 |
| `queries` | 1~3 条检索查询，第一条就是完整问题 |
| `filters` | 接口传入的硬过滤，始终生效 |
| `soft_filters` | 从问题里识别出的软过滤，已经解析成 doc_id / file_type |
| `scope_note` | 展示给用户的生效范围，例如“已限定在《部署手册》中检索” |
| `clarify_question` | intent=clarify 时返回给用户的反问 |

## 2. 流程

```
用户问题
  ↓ 规则预处理：归一化、去控制字符、长度检查
  ↓ 读取对话历史：最近 3 轮，按 token 截断
  ↓ 预处理 LLM（小模型，结构化输出，超时 3 秒；失败切备用模型再试一次）
  │    → intent / standalone_question / extra_queries / scope / clarify_question
  ↓ pydantic 校验；失败或超时则降级（§10）
  ↓ 生成 queries：[standalone_question] + extra_queries，去重
  ↓ 解析 scope：文件类型查同义词表，文档标题到登记表里匹配 → soft_filters
  ↓ 路由：
       rag     → retrieve
       chat    → generate（闲聊模式，不检索）
       clarify → 返回 clarify_question → postprocess 保存本轮
```

## 3. 规则预处理

| 规则 | 处理 |
|------|------|
| 首尾空白 | 去掉 |
| 零宽字符、控制字符 | 去掉 |
| NFKC 归一化 | 全角字母数字转半角，和清洗阶段对文档的处理保持一致 |
| 空问题 | 直接返回提示，不进入后续流程 |
| 超过 2000 字 | 直接返回“问题过长，请精简后再问” |

## 4. 对话历史

- 由 LangGraph checkpointer（SQLite）按 `session_id` 保存完整的消息列表。
- 送进预处理 LLM 的只是截断后的版本：最近 3 轮（一问一答算一轮），每条助手回答截断到 300 token，历史总共不超过 1500 token。
- 做指代消解只需要知道上文聊了什么，不需要完整的回答。
- 上一轮的 intent 也保存在会话状态里，用来防止连续反问（§6）。

## 5. 预处理 LLM 调用

### 5.1 模型

- 用 `config.yaml` 的 `llm.scenes.preprocess`：OpenAI 兼容接口的小模型，一个主模型、一个备用模型，和生成模型分开配置（见[大模型生成](大模型生成.md) §3）。
- 用 LangChain 的 `with_structured_output(Preprocessed)` 输出结构化结果，方式由接入点的 `structured_output` 决定（默认 function_calling），比让模型自由输出 JSON 更稳定。
- `temperature=0`，每次调用超时 3 秒，不重试：主模型失败、超时或输出校验失败，直接切备用模型试一次；备用也失败就按 §10 降级。

### 5.2 输出结构

```python
from typing import Literal
from pydantic import BaseModel, Field, field_validator

class Scope(BaseModel):
    doc_titles: list[str] = Field(default_factory=list)
    file_types: list[str] = Field(default_factory=list)

    @field_validator("doc_titles", "file_types")
    @classmethod
    def _cap(cls, v: list[str]) -> list[str]:
        # 用截断而不是 max_length：超量时不让整次调用校验失败
        return [s.strip()[:100] for s in v if s.strip()][:5]

class Preprocessed(BaseModel):
    intent: Literal["rag", "chat", "clarify"] = "rag"
    standalone_question: str
    extra_queries: list[str] = Field(default_factory=list)
    scope: Scope = Field(default_factory=Scope)
    clarify_question: str | None = None

    @field_validator("standalone_question")
    @classmethod
    def _cap_question(cls, v: str) -> str:
        return v.strip()[:500]

    @field_validator("extra_queries")
    @classmethod
    def _cap_queries(cls, v: list[str]) -> list[str]:
        # 超长、超量直接截断，不因为这类问题让整次调用失败。
        # 这里多留几条，去重后再由 build_queries 截到 3 条，避免重复查询占掉名额
        return [q.strip()[:200] for q in v if q.strip()][:4]
```

`standalone_question` 为空或 intent 不在三个取值里时，按 §10 降级。

### 5.3 Prompt 要点

完整内容见 `prompts/v1/preprocess_system.j2` 和 `preprocess_user.j2`（模板管理和转义规则见 [Prompt 组装](Prompt%20组装.md) §5、§12）。要点：
- intent 拿不准时一律选 rag。
- standalone_question 只补全指代和省略，不添加历史里没有的信息。
- scope 只在用户明确要求限定范围时才填，照原样写出用户的说法，由代码解析（§8）。
- 历史和问题分别放在 `<history>`、`<question>` 标签里，经过 `esc` 过滤器转义；Prompt 声明其中的指令都不执行。

重试改写的模板是 `rewrite_system.j2` 和 `rewrite_user.j2`（§9）。

例子：

| 历史 | 问题 | 输出 |
|------|------|------|
| 无 | 你好 | intent=chat |
| 在聊 Milvus 的 DISKANN | 它的内存怎么估算？ | standalone=“Milvus DISKANN 索引的内存怎么估算？” |
| 无 | 部署手册里 Docker 和裸机安装有什么区别 | standalone=原问题；extra=[“Docker 安装步骤”, “裸机安装步骤”]；scope.doc_titles=[“部署手册”] |
| 无 | PPT 里讲的架构图 | standalone=“PPT 中介绍的系统架构图”；scope.file_types=[“PPT”] |
| 无 | 怎么弄 | intent=clarify；clarify_question=“你想了解哪方面的操作？比如部署、配置还是使用？” |

## 6. 意图路由

| intent | 去向 | 说明 |
|--------|------|------|
| rag | `retrieve` | 默认路径 |
| chat | `generate`（闲聊模式） | 不检索，也不带上下文；Prompt 要求它不回答知识性问题，引导用户提问 |
| clarify | `clarify` 节点 → `postprocess` → END | 直接返回 `clarify_question`，后处理保存这一轮 |

- 防止连续反问：上一轮已经是 clarify 时，本轮即使判断为 clarify 也改成 rag，带着现有信息去检索。
- 误判为 chat 的代价最大（知识问题没有检索，模型可能凭空作答），所以 Prompt 要求拿不准时选 rag，评测时单独统计这类误判（§15）。

## 7. 生成查询

```python
import unicodedata

def _key(q: str) -> str:
    return "".join(unicodedata.normalize("NFKC", q).lower().split())

def build_queries(p: Preprocessed) -> list[str]:
    out, seen = [], set()
    for q in [p.standalone_question, *p.extra_queries]:
        q = unicodedata.normalize("NFKC", q)   # LLM 输出也做一次归一化，和文档保持一致
        if q and _key(q) not in seen:
            seen.add(_key(q))
            out.append(q)
    return out[:3]
```

- 第一条固定是完整问题，保证至少有一条查询和用户原意一致。
- 去重时忽略大小写、空白和全半角差异；先去重再截断，重复的扩展查询不会占掉名额。
- 每条查询都同时走稠密检索和 BM25（见[检索与重排](检索与重排.md) §4）。

## 8. 范围识别

LLM 只标出用户提到了什么（`scope`），由代码解析成真正的过滤条件。doc_id 只来自登记表，不来自 LLM 输出的文本。

### 8.1 文件类型

| 用户说法 | file_type |
|----------|-----------|
| PDF | pdf |
| Word、文档（明确指 Word 时） | doc, docx |
| PPT、幻灯片、演示文稿 | ppt, pptx |
| 图片、截图、照片 | png, jpg, jpeg |
| Markdown、md | md |
| 文本文件、txt | txt |

同义词表写在配置里；映射不到的说法直接忽略，结果再过一遍 `FILE_TYPES` 白名单。

### 8.2 文档标题

登记表新增 `title` 字段（见[数据清洗](数据清洗.md) §12），并建 SQLite FTS5 索引，同时索引标题和文件名：

```sql
CREATE VIRTUAL TABLE doc_titles USING fts5(
    doc_id UNINDEXED, title, filename, tokenize = 'trigram'
);
```

匹配步骤（每个 `doc_titles` 里的说法分别处理）：
1. 归一化：NFKC、去掉书名号和引号、去掉文件扩展名。
2. 精确匹配 `title` 或 `filename`。
3. 没有精确命中时，用 FTS5 trigram 召回前 20 个候选，再用 rapidfuzz 的 `partial_ratio` 打分，保留 ≥ 85 的。
4. 只考虑状态为 `indexed` 的文档。
5. 命中 1~5 个文档才生效；0 个或超过 5 个就放弃这个说法，记日志。

trigram 分词要求查询至少 3 个字符；太短的说法（例如“手册”）只做精确匹配。

### 8.3 软过滤和硬过滤

- 硬过滤：接口参数传入的 `filters`，始终生效。
- 软过滤：从问题里识别出的 `soft_filters`，只在第一次检索时生效，重试时去掉（§9）。

```python
def effective_filters(hard: dict | None, soft: dict | None) -> dict | None:
    if not soft:
        return hard
    if not hard:
        return soft
    merged = {}
    for key in ("file_types", "doc_ids"):
        h, s = hard.get(key), soft.get(key)
        if h and s:
            inter = sorted(set(h) & set(s))
            if not inter:        # 和硬过滤冲突：整个软过滤作废
                return hard
            merged[key] = inter
        elif h or s:
            merged[key] = h or s
    return merged
```

- 生效的软过滤写进 `scope_note`，例如“已限定在《部署手册》中检索”，随回答返回给前端，用户可以取消。
- 合并后的结果交给[检索与重排](检索与重排.md) §4.2 的 `build_expr`，再做一次白名单和正则校验。

## 9. 重试改写

grade 没通过（`top_score < 0.5`）且 `retry_count < 2` 时进入 `rewrite` 节点：

| 情况 | 处理 |
|------|------|
| 本轮用了软过滤，且还没去掉 | 只去掉软过滤，查询不变，`scope_note` 改成“限定范围内没有找到，已扩大到全部文档” |
| 其他 | 调用改写 LLM 生成新查询 |

一次只改一个变量：先放宽范围，再改查询，这样评测时能分清是哪一步起了作用。

改写 LLM：
- 模型、超时和切换规则与预处理相同（`llm.scenes.rewrite`：小模型，3 秒，失败切备用）。
- 输入：`standalone_question`、`tried_queries`、上一轮前 5 个候选的“文档标题 > 标题路径”（提示文档里实际用的说法）。
- 输出：`Rewrite`，每条查询最长 200 字（和 §5.2 一样用截断，不因超长让调用失败）；和 `tried_queries` 去重后再截到 `rewrite.max_queries` 条：

```python
class Rewrite(BaseModel):
    queries: list[str]

    @field_validator("queries")
    @classmethod
    def _cap(cls, v: list[str]) -> list[str]:
        return [q.strip()[:200] for q in v if q.strip()]
```

- 策略：问题太具体就泛化；复合问题拆开；参考候选的标题路径换用文档里的术语；中英文术语互换。
- 新查询去掉和 `tried_queries` 重复的（用 §7 的归一化规则比较）。如果去重后一条都不剩，或者调用失败，直接进入 `fallback`，不空转。

## 10. 降级

| 故障 | 处理 |
|------|------|
| 预处理主模型、备用模型都超时、报错或输出校验失败 | `intent=rag`，`standalone_question=原问题`，`queries=[原问题]`，不做范围识别 |
| 同上，且有对话历史 | 额外加一条查询“上一轮用户问题 + 本轮问题”，弥补没做指代消解的损失；重排仍用原问题 |
| 登记表不可用 | 跳过软过滤，只用硬过滤 |
| 改写主模型、备用模型都失败 | 直接进入 `fallback` |

降级都记日志并计数，接入[评估与监控](评估与监控.md)。

## 11. 安全

- 问题和历史放在 `<question>`、`<history>` 标签里，Prompt 声明其中的指令都不执行。
- LLM 的输出只影响查询文本和 `scope` 里的“说法”；真正进入 Milvus 表达式的 doc_id 和 file_type 只来自登记表和白名单。
- 所有输出字段都有长度和数量上限（§5.2），超出直接截断。
- API key 放在环境变量里。
- 日志记录 `session_id`、intent、查询和耗时；原始问题是否落盘按数据保留策略决定，默认只保留 30 天。

## 12. 延迟

| 步骤 | 估算 |
|------|------|
| 规则预处理、读历史 | < 5 ms |
| 预处理 LLM | 0.5~1 s（每次超时 3 s；主模型失败切备用时最多约 6 s） |
| 范围识别（FTS5 + rapidfuzz） | < 10 ms |
| 合计 | 约 0.5~1 s |

重试时如果调用了改写 LLM，每次再加 0.5~1 秒。加上检索和重排，最坏情况（重试 2 次）约 5~6 秒。

## 13. LangGraph 节点

D-003 A：节点统一接收 `(state, runtime: Runtime[Deps])`；依赖取 `runtime.context`，不使用模块级 cfg/客户端。Deps 字段由 `graph/deps.py` 定义：cfg、count、clients、sems、write、milvus、embed_client、rerank_client、registry、structured_call、prompt_env。D-013 B：metrics 只是读取全局指标的兼容属性，不是构造/replace字段；message_id 从 RunnableConfig.metadata 读取，不加进 Deps。结构化调用保持原四参数，测试使用 monkeypatch，prompt_env 默认按配置版本构建。事件使用 `runtime.stream_writer`；仅测试需要时覆盖 deps.write。

```python
def route_after_preprocess(state: RAGState) -> str:
    return {"rag": "retrieve", "chat": "generate", "clarify": "clarify"}[state["intent"]]

def route_after_rewrite(state: RAGState) -> str:
    return "retrieve" if state["queries"] else "fallback"

g.add_edge(START, "preprocess")
g.add_conditional_edges("preprocess", route_after_preprocess,
                        ["retrieve", "generate", "clarify"])
g.add_edge("clarify", "postprocess")   # 反问这一轮也要存进历史，防止连续反问（见 后处理.md §10）
g.add_conditional_edges("rewrite", route_after_rewrite, ["retrieve", "fallback"])
```

- `preprocess` 节点在每轮开始时重置本轮字段：`retry_count=0`、`tried_queries=[]`、`use_soft=True`、`hits=[]` 等，避免上一轮的结果残留。
- `prev_intent` 在重置前从上一轮状态里取出，用于防止连续反问。
- `rewrite` 节点负责 `retry_count + 1`，并把本轮查询加进 `tried_queries`。

## 14. 配置

所有参数都在项目根目录 `config.yaml` 的 `preprocess`、`rewrite` 段（包括文件类型同义词表），默认值以该文件为准。

## 15. 评测

使用[评估与监控](评估与监控.md) §3 由 LLM 生成的评测集，其中多轮、闲聊、反问、范围限定类题目自带 intent、期望的完整问题、期望的范围和答案所在原文片段的标签。

| 指标 | 说明 |
|------|------|
| intent 准确率 | 单独看 rag 被误判为 chat 的比例，这一项要尽量接近 0 |
| 指代消解效果 | 多轮问题上，用完整问题检索和用原问题检索的 Recall@8 对比 |
| 查询扩展效果 | 只用完整问题 vs 加上扩展查询的 Recall@30 对比 |
| 范围识别 | 精确率和召回率；重点看“识别错导致限定错了范围”的比例 |
| 重试改写 | 进入重试后最终通过 grade 的比例 |
| 延迟与降级 | 预处理 p50 / p95，降级率 |

## 17. 待讨论

- chat 模式的回答用哪个模型：预处理小模型还是生成模型，放到[大模型生成](大模型生成.md)里定。
- clarify 的触发尺度：评测后看反问是否太频繁，再调 Prompt。
- 范围识别目前只到文档和文件类型，“第三章里说的”这种章节级限定暂不支持。
- 同一份内容有中英文两个标题时，模糊匹配可能只命中一个，需要看实际数据。
