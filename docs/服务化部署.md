# 服务化部署

把手动起的三个进程变成开机自启、按依赖顺序启动的单机部署。决策见[总揽](总揽.md) §7“服务化部署（2026-10-05）”。

## 1. 范围

- 单机部署。主机为 32 核、30 GB 内存、RTX 4060 8 GB，所有组件都在这一台上。
- 只在本机访问。API、演示页、原文、图片、`/metrics` 都没有鉴权，只监听 127.0.0.1；需要从别的机器看时用 SSH 端口转发。
- 不在范围内：多机、高可用、反向代理、TLS、API 健康检查、监控栈（Prometheus / Grafana）、日志改造、备份、入库独占锁。§7 记下了这些暂缓项的现状。

## 2. 进程拓扑

| 组件 | 管理方式 | 监听 | 状态 / 数据 |
|------|----------|------|-------------|
| Milvus（etcd、MinIO、standalone） | `docker-compose.milvus.yml`，容器生命周期归用户（D-017） | `services.milvus.uri`，只绑 127.0.0.1 | `volumes/`、命名卷 `milvus_local` |
| 编码 + 重排 | systemd 用户单元 `ragagent-embed` | `services.embed.host` / `port` | 无状态；模型权重在 HF 缓存 |
| 问答 API + 演示页 | systemd 用户单元 `ragagent-api` | 127.0.0.1:8000 | `paths.session_db`、`paths.feedback_db`；只读 `paths.registry_db`、`paths.clean` |
| 离线入库 | 手动执行命令，低峰时跑（§5） | 不监听 | `paths.raw` / `parsed` / `clean` / `chunks`、登记表 |
| 外部依赖 | LLM 接入点（`llm.endpoints`）、Langfuse 云、MinerU 云 | — | 密钥在 `.env` |

- API 只能跑 1 个 worker。会话串行锁（`SessionLocks`）、LLM 并发上限（`llm.endpoints.*.max_concurrency`）和 Prometheus 指标（D-013 B）都在进程内，多 worker 会让同会话并发写 checkpoint、成倍突破接入点限额，指标也只能抓到其中一份。API 是异步的，一个进程能同时处理很多流式请求，吞吐瓶颈在 LLM 接入点和 GPU。
- 离线入库的编码同样走编码服务的 HTTP 接口，GPU 上只有一个模型进程。

## 3. 启动顺序

```
Milvus（compose healthy） → ragagent-embed（模型加载完，/health 200） → ragagent-api
```

- 不加专门的健康检查接口，依赖顺序靠 systemd 的 `After=` / `Requires=` 和失败重启：
  - API 在 lifespan 里连接 Milvus，Milvus 没起来时进程启动失败，systemd 按 `RestartSec` 重试，等 Milvus 起来后自然成功。
  - 编码服务在模型加载完之前 `/health` 返回 503。API 启动时不调编码服务，所以编码服务没加载完时 API 能起来，但这段时间走检索的问答会返回“服务暂时不可用，请稍后再试”，模型加载完以后自动恢复。
- Milvus 开机自启由用户决定（D-017），compose 文件不加 `restart` 策略。

## 4. systemd 用户单元

单元文件在仓库的 `deploy/systemd/`：

| 文件 | 作用 | 依赖 |
|------|------|------|
| `ragagent-embed.service` | 编码 + 重排服务，`python -m ragagent.index.embed_service` | 无 |
| `ragagent-api.service` | 问答 API + 演示页，uvicorn 工厂模式，`--workers 1` | `After=` / `Requires=` 编码服务 |

- 文件里的 `%h/code/ragagent`（仓库路径）和 `%h/.local/bin/uv`（uv 路径）按实际情况改。
- 端口和地址只在 `config.yaml` 里改：编码服务读 `services.embed`；API 的监听地址目前写在单元文件的命令行参数里，只能是 127.0.0.1（§1）。
- 两个单元都是 `Restart=on-failure`、`RestartSec=10`。

安装和日常操作：

```bash
mkdir -p ~/.config/systemd/user
cp deploy/systemd/*.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now ragagent-embed ragagent-api
loginctl enable-linger "$USER"        # 不登录也开机启动用户单元
systemctl --user status ragagent-api
journalctl --user -u ragagent-api -f  # 看日志
systemctl --user restart ragagent-api # 改了代码或 config.yaml 之后
```

- 密钥只通过 `--env-file .env` 读取，单元文件里不写。
- `Requires=` 让编码服务停掉时 API 跟着停；只重启 API 不影响编码服务（模型加载要几十秒，尽量少重启它）。
- 改了 `deploy/systemd/` 里的文件要重新复制并 `daemon-reload`。

## 5. 离线入库与 GPU 共享

- 入库命令手动执行。入库和在线请求共用编码服务的 GPU 和进程内互斥锁，大批量入库期间在线请求的编码和重排延迟会上升，所以大批量入库放在低峰跑。
- 目前没有入库独占锁：同时跑两条清洗或写索引命令会同时改登记表、同时写同一个 collection，需要人工避免（§7）。

## 6. 本机检查

```bash
systemctl --user is-active ragagent-embed ragagent-api
curl -s http://127.0.0.1:8001/health                 # 端口以 services.embed.port 为准
curl -s http://127.0.0.1:8000/api/docs | head -c 200  # API 和登记表都正常时返回文档列表
```

## 7. 暂缓项与已知问题

| 项 | 现状 | 以后要做时 |
|----|------|------------|
| 访问控制 / TLS | 无鉴权，只监听本机 | 反向代理加认证和 TLS；原文、图片、反馈接口与问答用同一套控制；SSE 需关闭代理缓冲 |
| API 健康检查 | 没有专门接口，靠 systemd 失败重启 | 加 live / ready 两个接口，ready 检查 Milvus、编码服务和登记表，不探测 LLM |
| 监控栈 | `/metrics` 和 `scripts/gen_alerts.py` 已有，没有 Prometheus / Grafana | compose 起 Prometheus + Grafana，只绑本机；GPU 指标用 nvidia-smi exporter，Milvus 内存和 GPU 告警的指标名要实测后对齐 |
| 日志 | journald 收集标准输出；`logging.retain_days`、`logging.prompt_sample_rate` 在配置里但**代码没有实现** | 保留期交给 journald；抽样记录只写本地，不进 Langfuse |
| 会话库 | `paths.session_db` 没有清理机制，会一直增长 | 按最后活跃时间清理 |
| 入库独占锁 | 未做，靠人工避免同时跑两个入库任务 | 清洗和写索引命令启动时拿 `flock` 文件锁，拿不到立即退出；进程退出自动释放 |
| 备份 | 未做 | 登记表、反馈库用 SQLite 在线备份；Milvus 靠从 chunk 重建，重建耗时要实测 |
