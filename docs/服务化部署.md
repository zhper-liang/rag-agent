# 服务化部署

把手动起的三个进程变成开机自启、按依赖顺序启动的单机部署。现行决策见[总揽](总揽.md) §7“服务化部署”与“M5 补完”。

## 1. 范围

- 单机部署。主机为 32 核、30 GB 内存、RTX 4060 8 GB，所有组件都在这一台上。
- 只在本机访问。API、演示页、原文、图片、`/metrics` 都没有登录鉴权（上传接口另有请求头与来源校验，§11.2），只监听 127.0.0.1；需要从别的机器看时用 SSH 端口转发。
- 已实现：入库独占锁、live / ready 健康检查、SQLite 在线备份、本地完整 Prompt / 回答抽样、Prometheus / Grafana / GPU exporter（2026-10-19）。
- 不在范围内：多机、高可用、反向代理、TLS、鉴权与会话库自动清理。运行参数只在 `config.yaml`；监控原生配置由它生成，不手工维护副本。

## 2. 进程拓扑

| 组件 | 管理方式 | 监听 | 状态 / 数据 |
|------|----------|------|-------------|
| Milvus（etcd、MinIO、standalone） | `docker-compose.milvus.yml`，容器生命周期归用户（D-017） | `services.milvus.uri`，只绑 127.0.0.1 | `volumes/`、命名卷 `milvus_local` |
| 编码 + 重排 | systemd 用户单元 `ragagent-embed` | `services.embed.host` / `port` | 无状态；模型权重在 HF 缓存 |
| 问答 API + 演示页 | systemd 用户单元 `ragagent-api` | 127.0.0.1:8000 | `paths.session_db`、`paths.feedback_db`；只读 `paths.registry_db`、`paths.clean` |
| 离线入库 | 手动执行命令，低峰时跑（§5） | 不监听 | `paths.raw` / `parsed` / `clean` / `chunks`、登记表 |
| 外部依赖 | LLM 接入点（`llm.endpoints`）、Langfuse 云、MinerU 云 | — | 密钥在 `.env` |

- API 只能跑 1 个 worker。会话串行锁（`SessionLocks`）、LLM 并发上限（`llm.endpoints.*.max_concurrency`）和 Prometheus 指标（D-013 B）都在进程内，多 worker 会让同会话并发写 checkpoint、成倍突破接入点限额，指标也只能抓到其中一份。API 是异步的，一个进程能同时处理很多流式请求，吞吐瓶颈在 LLM 接入点和 GPU。
- 离线入库的编码同样走编码服务的 HTTP 接口，GPU 上只有一个模型进程。

## 3. 启动顺序

```
Milvus（compose healthy） → ragagent-embed（模型加载完，/health 200） → ragagent-api
```

- systemd 的 `After=` / `Requires=` 只保证进程顺序，不代表依赖就绪；部署后通过 `GET /api/health/ready` 验收：
  - API 在 lifespan 里连接 Milvus，Milvus 没起来时进程启动失败，systemd 按 `RestartSec` 重试，等 Milvus 起来后自然成功。
  - 编码服务在模型加载完之前 `/health` 返回 503。API 启动时不调编码服务，所以编码服务没加载完时 API 能起来，但这段时间走检索的问答会返回“服务暂时不可用，请稍后再试”，模型加载完以后自动恢复。
- Milvus 开机自启由用户决定（D-017），compose 文件不加 `restart` 策略。

## 4. systemd 用户单元

单元文件在仓库的 `deploy/systemd/`：

| 文件 | 作用 | 依赖 |
|------|------|------|
| `ragagent-embed.service` | 编码 + 重排服务，`python -m ragagent.index.embed_service` | 无 |
| `ragagent-api.service` | 问答 API + 演示页，uvicorn 工厂模式，`--workers 1` | `After=` / `Requires=` 编码服务 |
| `ragagent-backup.service` / `.timer` | 每日 SQLite 在线备份，补跑错过的定时任务 | 库可缺省；缺失跳过，不创建空库 |
| `ragagent-gpu.service` | 本机 nvidia-smi exporter，仅监听回环 | NVIDIA 驱动与 `nvidia-smi` |

- 文件里的 `%h/code/ragagent`（仓库路径）和 `%h/.local/bin/uv`（uv 路径）按实际情况改。
- 端口和地址只在 `config.yaml` 里改：编码服务读 `services.embed`；API 的监听地址目前写在单元文件的命令行参数里，只能是 127.0.0.1（§1）。
- API、编码与 GPU exporter 使用失败重启；备份是 oneshot，由 timer 调度。运行输出由 journald 收集，保留策略由主机 journald 配置管理。

安装和日常操作：

```bash
mkdir -p ~/.config/systemd/user
cp deploy/systemd/*.service deploy/systemd/*.timer ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now ragagent-embed ragagent-api ragagent-gpu
systemctl --user enable --now ragagent-backup.timer
loginctl enable-linger "$USER"        # 不登录也开机启动用户单元
systemctl --user status ragagent-api
journalctl --user -u ragagent-api -f  # 看日志
systemctl --user restart ragagent-api # 改了代码或 config.yaml 之后
```

- 密钥只通过 `--env-file .env` 读取，单元文件里不写。
- `Requires=` 让编码服务停掉时 API 跟着停；只重启 API 不影响编码服务（模型加载要几十秒，尽量少重启它）。
- 改了 `deploy/systemd/` 里的文件要重新复制并 `daemon-reload`。

### 4.1 前端构建

前端源码在 `web/`，构建产物输出到 `src/ragagent/api/static/`，不提交（[总揽](总揽.md) §4.3，D-020）。部署机器要装 Node（版本见 `web/package.json` 的 `engines`）。首次部署和每次拉取前端改动后：

```bash
cd web
npm ci
npm run build
systemctl --user restart ragagent-api
```

- 没有构建产物时 API 照常启动，`/`、`/c/*`、`/d/*` 返回 503 和“前端未构建”提示，问答接口不受影响。
- 构建只产出静态文件，不引入 Node 运行时进程；CSP 与同源部署不变。

## 5. 离线入库与 GPU 共享

- 入库命令手动执行。入库和在线请求共用编码服务的 GPU 和进程内互斥锁，大批量入库期间在线请求的编码和重排延迟会上升，所以大批量入库放在低峰跑。
- 清洗、写索引和独立切分 CLI 启动写操作前，对 `paths.ingest_lock` 取得 `flock(LOCK_EX | LOCK_NB)`；拿不到立即非零退出，进程退出自动释放。锁文件不删除，避免 inode 竞争。
- 锁在 CLI 边界，不在可组合的 `run_clean` / `run_index` 中重复加锁；自编排调用库函数时，调用者须在整段入库事务外持有同一把锁。CLI 与定时备份各有独立锁：SQLite 备份可和在线服务/入库共存。

## 6. 本机检查

```bash
systemctl --user is-active ragagent-embed ragagent-api
curl -s http://127.0.0.1:8001/health                 # 端口以 services.embed.port 为准
curl --fail --silent --show-error http://127.0.0.1:8000/api/health/live
curl --fail --silent --show-error http://127.0.0.1:8000/api/health/ready
uv run --env-file .env python scripts/check_health.py
```

### 6.1 健康语义

- `/api/health/live`：进程能处理请求就返回 200，不请求任何外部服务。
- `/api/health/ready`：并发检查 Milvus 正式别名解析且可查询、编码服务 `/health`、登记表只读查询。每项上限取 `api.health_timeout_s`，全成功返回 200，否则返回 503 并带 `checks.milvus` / `embed` / `registry` 的状态与原因类型；不返回异常原文，不探测 LLM。
- SQLite 和同步 Milvus 调用在线程内执行；同项尚未结束的探测任务复用，避免超时后堆积线程。依赖恢复后下次探测可自动成功。

## 7. 暂缓项与已知问题

| 项 | 现状 | 处理方式 |
|----|------|----------|
| 访问控制 / TLS | 无鉴权，只监听本机 | 仍不做；对外开放前统一保护问答、原文、图片与反馈接口，SSE 需关闭代理缓冲 |
| API 健康检查 | live / ready 已实现 | 依赖就绪以 ready 为准；不以 systemd active 代替 |
| 监控栈 | Prometheus / Grafana compose + GPU exporter + 预置看板已实现 | 本机部署见 §10；告警在 Prometheus 中评估，本轮不接 Alertmanager/外部通知渠道 |
| 日志 | journald 收标准输出；完整 Prompt / 回答仅按比例写本地 | 比例和文件轮转见 `logging.*`，journald 自管运行日志保留期 |
| 会话库 | 无自动清理，前端删除只影响 localStorage | 接受增长；停服后按需处理，操作前先备份 |
| 入库独占锁 | 三个 CLI 已共享同一 flock | 库级组合调用者显式持锁，见 §5 |
| 同步 SQLite 占事件循环 | 反馈、登记表和健康检查均在线程执行 | 已修 |
| 备份 | 三个 SQLite 库在线备份，Milvus 从 chunk 重建 | 保留份数见 `backup.keep`；实测见 §9 |

### 7.1 阻塞隔离与超时边界

- API 内的登记表查询、反馈写入、健康探测以及预处理范围解析通过 `asyncio.to_thread` 执行，避免同步 SQLite 等待阻塞事件循环。WAL 读写和反馈库写锁仍遵循 SQLite 本身的锁语义，线程隔离不等于没有锁等待。
- `api.request_timeout_s` 约束整次问答；超时取消图任务，发送 `error` 事件并结束 SSE。LLM 首 token、Milvus 调用和编码 HTTP 各自还有超时，见[大模型生成](大模型生成.md)与[检索与重排](检索与重排.md)。
- GPU 争用会影响检索延迟；`retrieval.timeout_ms` 是超时预算，不是延迟保证。调整这些预算会改变 p95 与配置哈希，必须重跑评测，不能沿用旧基线冒充当前结果。
- 浏览器删除会话只删除 localStorage，不删除服务端 checkpoint；会话库不自动清理。需要手工清空时，先停止 API、备份 `paths.session_db`，再处理数据库及其 WAL/SHM 文件，避免在线删除活动库。

## 8. 本地抽样与运行日志

- `logging.prompt_sample_rate` 决定生成请求的抽样比例；关闭时不创建文件。生成节点把完整 `PromptPackage`（含多模态内容）、回答与状态写到 `logging.sample_path`，不会把它们加进 trace/state/checkpoint。
- 抽样文件为 JSONL；单文件大小、历史文件数分别由 `logging.sample_max_mb`、`logging.sample_keep_files` 控制。单条大记录为保持完整可能超过文件上限。新文件权限为仅用户读写；包含资料原文，应留在本机受控目录，不提交或上传。
- 写盘在线程内执行，抽样故障只记异常类型，不中断回答；禁止标准 logging 错误回退打印原文。Langfuse 始终使用遮掩客户端，见[评估与监控](评估与监控.md) §9。
- 普通运行日志保留期交给 journald，不再由应用实现定期删除。

## 9. 备份与恢复

- `scripts/backup.py` 读取 `backup.dbs`，通过 `paths` 下同名键定位登记表、反馈库和会话库，调用 SQLite 在线 backup API，包含 WAL 中已提交的数据。缺失库跳过且不创建空库；损坏库报错并以非零退出，不发布半成品、不删除旧快照。
- 快照写到 `backup.dir`，成功校验后原子发布，每库只保留 `backup.keep` 份。备份并发由目录内文件锁拒绝，文件权限仅用户读写；定时由 `ragagent-backup.timer` 调用，错过时补跑。

```bash
uv run --env-file .env python scripts/backup.py
systemctl --user list-timers ragagent-backup.timer
systemctl --user start ragagent-backup.service
```

- 恢复 SQLite：先停 API 和离线入库，保留当前库及其 WAL/SHM 以便回退，再把选定快照复制到对应 `paths.*_db`；不要让旧 WAL/SHM 覆盖恢复库。确认权限与完整性后重启，并通过 ready 检查。
- SQLite 快照是各库独立一致，不是三个库的跨库原子快照。Milvus 不打包备份：保留 `paths.chunks`、`paths.clean`、原始/解析资料、配置及模型版本；用新集合重建，验收后再按[向量化建库](向量化建库.md) §8 切别名。重建 CLI 同样持入库锁，不自动切正式别名。
- **2026-10-19 实测**：登记表只读在线副本、独立临时集合、真 Visualized-BGE 编码，从当前 chunk 重建 **97 文档 / 2585 chunks 用时 85.05 秒**（含 DISKANN/BM25 索引等待与 load）；索引每字段均 2585 行，无错误。正式 `rag_chunks` 别名前后均指向原集合，临时集合测后删除。记录在本机 `data/reports/m5_rebuild.json`。这是小语料样本，不外推千万级恢复时限。

## 10. 监控栈

- 所有可调参数集中于 `monitor.stack`，阈值仍在 `monitor.alerts`；`scripts/gen_monitoring.py` 复用 `scripts/gen_alerts.py` 生成 compose、抓取配置、规则与 Grafana provisioning 到 `deploy/monitoring/generated/`（gitignored）。改配置后重新生成并重新部署，不手改生成文件。
- Grafana 管理密码只通过 `monitor.stack.grafana_password_env` 指定的环境变量注入，变量名列在 `.env.example`，生成器不写密码。若验证时未设置该变量，本机验证密码写在 gitignored 的私密文件 `data/monitoring/grafana-password`；正式启用时请自行设置环境变量。
- 默认适配当前 Docker Desktop：bridge 网络，Prometheus/Grafana 端口仅发布到主机回环；容器内必须监听容器接口才能通过端口映射访问，不代表对外发布。API、Milvus、GPU exporter 通过 `host.docker.internal` 访问，必须保持主机服务仅回环监听，并验证实际可达。
- 原生 Linux 如 bridge 无法访问回环服务，将 `monitor.stack.network_mode` 改为 host，并把三项 target 改成回环地址；host 模式下 Prometheus/Grafana 自身也只绑定回环。不为监控把 API 改成 `0.0.0.0`。
- GPU exporter 运行在宿主机，用 `nvidia-smi` 读取显存，不要求容器 GPU runtime 或 DCGM；端口和命令超时读 `monitor.stack`。指标为 `rag_gpu_memory_used_bytes` / `rag_gpu_memory_total_bytes`；Milvus 真实内存指标为 `process_resident_memory_bytes{job="milvus"}`。告警与看板使用同一套名称。
- 看板源文件 `deploy/monitoring/dashboard.json`：阶段延迟 p50/p95/p99、错误率、降级率、GPU 显存、Milvus RSS；Prometheus 规则由配置生成，不在看板复制阈值。

```bash
uv run --env-file .env python scripts/gen_monitoring.py
# GRAFANA_ADMIN_PASSWORD 必须已设置；--env-file 只用于 compose 的变量替换
docker compose --env-file .env -p ragagent-monitoring -f deploy/monitoring/generated/compose.yml up -d
# 规则和抓取配置校验
docker compose --env-file .env -p ragagent-monitoring -f deploy/monitoring/generated/compose.yml exec prometheus promtool check config /etc/prometheus/prometheus.yml
```

- 本机验收：三个 scrape target（ragagent / milvus / gpu）均 up；Grafana provisioning 看板可读。告警只在 Prometheus 内评估，通知渠道需后续单独配置。

## 11. 网页上传（D-021）

演示页可以上传文档，后台按清洗 → 切分 → 写索引跑完整条入库链路。参数在 `api.upload`、`paths.uploads`。

### 11.1 接口

- `POST /api/uploads`：multipart，一次最多 `api.upload.max_files` 个文件，单个不超过 `api.upload.max_file_mb`。返回 `job_id`，不等入库完成。
- `GET /api/uploads/{job_id}`：任务状态 `queued / cleaning / chunking / indexing / done / failed / interrupted`，逐文件给出结果（`created / updated / unchanged / duplicate / failed`）和简短原因，不带异常原文。
- `GET /api/uploads`：最近的任务列表，供页面恢复进度；任务记录保留 `api.upload.jobs_keep` 条。

### 11.2 访问控制

不做登录（§1 仍只监听本机），但上传是写接口，额外做三项检查，任一不过返回 403：

- 必须带 `api.upload.client_header` 指定的请求头。浏览器表单发不出自定义头，跨站 `fetch` 带自定义头会触发 CORS 预检，而 API 不返回任何 CORS 头，所以外站页面发不进来。
- 有 `Origin` 时必须与请求的 `Host` 同源。
- `Host` 只接受 `127.0.0.1`、`localhost`（带端口），挡 DNS rebinding。

### 11.3 文件名与存放

- 只取文件名本身，丢掉任何路径部分；NFC 规范化；去掉控制字符和 `/ \ : * ? " < > |`，合并连续空白，去掉首尾空格和点。
- 不能以 `.` 开头，清洗后为空的拒绝；主名超过 `api.upload.max_name_chars` 截断，保留后缀；后缀转小写后必须在 `ingest.parse_routes` 里。
- 同一请求里清洗后重名的，整次拒绝。
- 文件存到 `paths.uploads/{清洗后的文件名}`，不建子目录。`paths.uploads` 和 `paths.raw` 平级、互不包含，是独立的扫描根：登记的 `source_path` 和 `doc_id` 用 `@uploads/{文件名}` 计算（加前缀，避免和 `raw/` 顶层同名文件撞 `doc_id`），缺失判定只作用于它自己登记过的文档（`ingest_sources.input_root`），CLI 全量扫描 `raw` 不会误删或重复登记上传的文件。

### 11.4 同名文件

`doc_id` 由清洗后的文件名决定，同名即同一文档：

| 情况 | 结果 |
|------|------|
| 同名、内容相同 | 不重新处理，结果为 `unchanged` |
| 同名、内容不同 | 默认 409，返回已有文档的标题和版本；前端让用户选“覆盖为新版本”（带 `overwrite=true` 重新提交）或“改名后上传” |
| 不同名、内容相同 | 登记为新文档，状态 `duplicate`，不进索引 |

409 在写盘之前判断：被拒绝的文件不落盘，不建任务。

### 11.5 任务执行

- API 进程内一个串行队列，一次只跑一个任务。任务在同一次 `ingest_lock` 持有期内跑完清洗、切分、写索引；拿不到锁（CLI 正在入库）就保持 `queued`，每 `api.upload.lock_retry_s` 秒重试一次，不报错。
- 清洗对 `paths.uploads` 调 `run_clean`；PDF / Word / PPT / 图片上传到 MinerU 云端（已确认可以上传）。云端长时间 pending 时沿用清洗的超时与 `parsing` 恢复。
- 写索引和在线问答共用编码服务，入库期间问答的编码和重排延迟会上升（§5）。
- 任务状态存 SQLite（`paths.registry_db` 同库的扩展表 `upload_jobs`，不改 `documents` 列）。API 重启时，未结束的任务标 `interrupted`，页面可重试；重试走清洗的断点恢复，不重复上传已提交的 MinerU 批次。
- 完成后前端刷新文档列表；新文档立即可作为检索范围。
