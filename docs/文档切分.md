# 文档切分

## 1. 目标

把[数据清洗](数据清洗.md)输出的 Block 序列切成适合检索的 chunk：
- 结构优先：先按标题树切，章节能整块放下就整块放下。
- 不破坏完整性：段落、代码块、表格、列表、公式是不可拆分的单元，只有单个单元超过 max 时才递归拆分。
- 大小可控：用 target / max 两个预算控制 chunk 大小。
- 图片单独成 chunk，元数据指向附近的文本 chunk，文本 chunk 也反向记录图片。

- 输入：`data/clean/{doc_id}/v{version}/clean.json`（CleanDocument）
- 输出：`data/chunks/{doc_id}/v{version}.jsonl`（每行一个 Chunk）

## 2. 预算

| 参数 | 默认值 | 含义 |
|------|--------|------|
| `target_tokens` | 400 | 目标大小。贪心合并时累积到这里就停下 |
| `max_tokens` | 800 | 硬上限。任何 chunk 都不能超过；只有为了保持完整性才允许超过 target |
| `min_tokens` | 64 | 小于这个值的 chunk 尽量并入相邻 chunk |
| `overlap_tokens` | 64 | 只在递归拆分超长单元时使用，结构边界之间不做重叠 |
| `inline_code_tokens` | 48 | 不超过这个大小的代码块视为行内代码，跟着正文合并，不单独成 chunk |

- token 用 bge-m3 的 tokenizer 计数（Visualized-BGE 的文本塔与它一致）。
- `max_tokens` 算的是 chunk 正文，向量化时还会加上标题路径前缀（通常 20~50 token），所以 max 要给前缀留余量。Visualized-BGE 文本输入的最大长度需要在向量化阶段确认，确保 `max_tokens + 前缀` 不超过它。
- 默认值只是起点，之后在评测集上对比 target=256 / 400 / 600 的召回率再定（见 §13）。

## 3. 总体流程

```
Block 序列
  ↓ ① 建标题树：heading 成为节点，其他 Block 挂到最近的标题下
  ↓ ② 组装单元：相邻且强关联的 Block 绑成一个不可拆分的 Unit；图片抽出来，原位置留占位符
  ↓ ③ 超长单元递归拆分：单个 Unit 超过 max 时，按类型拆开
  ↓ ④ 层级合并：自上而下，能整节放下就整节放下，放不下就进入子节；叶子节内做语义 + 贪心合并
  ↓ ⑤ 收尾：过小的 chunk 并入相邻 chunk；生成 embed_text；分配 chunk_id
  ↓ ⑥ 图片 chunk：生成图片 chunk，和附近的文本 chunk 双向关联
  ↓ ⑦ 去重
Chunk 列表
```

## 4. 数据模型

```python
import re
from typing import Literal
from pydantic import BaseModel, Field

ChunkType = Literal["text", "code", "image"]
CHUNK_ID_RE = re.compile(r"^([0-9a-f]{16}):v(\d+):(\d{5})$")

def make_chunk_id(doc_id: str, version: int, seq: int) -> str:
    cid = f"{doc_id}:v{version}:{seq:05d}"
    if not CHUNK_ID_RE.fullmatch(cid):
        raise ValueError(f"非法 chunk_id: {cid}")
    return cid

def parse_chunk_id(cid: str) -> tuple[str, int, int]:
    if not (m := CHUNK_ID_RE.fullmatch(cid)):
        raise ValueError(f"非法 chunk_id: {cid}")
    return m.group(1), int(m.group(2)), int(m.group(3))

class Chunk(BaseModel):
    chunk_id: str = Field(pattern=CHUNK_ID_RE.pattern)  # make_chunk_id(doc_id, version, seq)，确定性生成，重切时可按 doc_id 整体删除
    doc_id: str = Field(pattern=DOC_ID_PATTERN)
    version: int
    seq: int                    # 文档内顺序
    type: ChunkType
    text: str                   # 原文（Markdown），给 LLM 和前端展示用
    embed_text: str             # 向量化用：标题路径 + 上下文前缀 + text
    content_hash: str           # text 归一化后的 sha256（§11），召回后去重用
    tokens: int                 # text 的 token 数（bge-m3 计数），上下文构造算预算用
    section_path: list[str]     # ["第2章 部署", "2.1 环境准备"]
    section_idx: int            # 所在节在文档内的编号（标题树先序遍历顺序），整节取回用
    section_tokens: int         # 所在节的总 token 数，决定能否整节放入上下文
    page_start: int | None
    page_end: int | None
    prev_id: str | None = None  # 同一文档中前后相邻的 text/code chunk
    next_id: str | None = None
    image_ids: list[str] = Field(default_factory=list)    # 本 chunk 关联的图片 chunk
    related_ids: list[str] = Field(default_factory=list)  # 代码与引导段落等互相关联的 chunk
    image_path: str | None = None  # 仅 image chunk
    searchable: bool = True     # 文档内重复、模板文本为 False（§11）：不参与检索，保留给上下文扩展
    meta: dict = Field(default_factory=dict)  # strategy、split_part、overlap_chars、lead_in、lang、anchor_id 等
```

`make_chunk_id` / `parse_chunk_id` 是 chunk_id 唯一的构造和解析入口，其他模块不要自己拼字符串。

合并阶段（§9）先产出 `Draft`，收尾（§9.4）再统一编号、串链、生成 `embed_text` 和 `content_hash`，变成 `Chunk`：

```python
class Draft(BaseModel):
    type: ChunkType
    text: str
    blocks: list[Block]         # 来源 Block：算页码、找图片占位符
    tokens: int
    section_path: list[str]
    section_idx: int
    section_tokens: int
    image_path: str | None = None
    meta: dict = Field(default_factory=dict)  # strategy、split_part、overlap_chars、lead_in、lang 等
```

`section_idx` / `section_tokens` 的取值：
- 普通 chunk：它所在的节（整节 chunk 就是它自己那一节）。
- 小兄弟节合并成的 chunk：共同的父节，和 `section_path` 取共同父节路径保持一致。
- 图片 chunk：和锚点 chunk 相同。

`meta.strategy` 记录这个 chunk 是怎么产生的：`section`（整节）/ `semantic` / `greedy` / `split`（递归拆分）/ `code` / `image`，便于评测时按策略分析效果。

## 5. 标题树

```python
class Section(BaseModel):
    heading: str | None          # 根节点为 None（对应文档标题之前的内容）
    level: int
    path: list[str]              # 从根到本节的标题列表
    idx: int                     # 先序遍历编号，根节点为 0
    body: list[Block]            # 本节标题之后、第一个子标题之前的 Block
    children: list["Section"]
    tokens: int = 0              # 整节（含所有子节和标题行）的 token 数，自底向上计算
```

- 标题层级沿用清洗阶段修正后的 `Block.level`。遇到跳级（1 级直接到 3 级），就挂到最近的更高层级下面。
- 没有任何标题的文档（TXT、部分图片 OCR 结果）只有一个根节点，直接进入叶子节合并。
- 空章节（只有标题没有正文，也没有子节）：标题不单独成 chunk，只保留在后续 chunk 的 `section_path` 里；如果后面也没有内容，直接丢弃。

## 6. 单元与绑定规则

Unit 是合并时最小的不可拆分单位，由一个或多个 Block 组成。

```python
class Unit(BaseModel):
    blocks: list[Block]
    kind: Literal["text", "code", "table", "list", "equation"]
    tokens: int
    hard_break: bool = False   # True 时前后都必须断开（大代码块）
```

以下情况把相邻 Block 绑成一个 Unit，前提是绑定后不超过 max；超过就解除绑定，退回单独的 Unit：

| 情况 | 例子 |
|------|------|
| 段落以冒号结尾，后面紧跟列表或表格 | “支持以下参数：” + 参数列表 |
| 公式和前后的解释段落 | “损失函数定义为” + 公式 + “其中 x 表示……” |
| 表格和它的标题、脚注 | 清洗阶段已放进 `meta`，拼回文本 |
| 列表 | 清洗阶段已经是一个 list Block |

图片不参与绑定：从流里抽出来，原位置留一个占位符 `[图: {caption}]`（只占几个 token），后面在 §10 里建立关联。

## 7. 按类型处理

### 7.1 普通文本（段落、列表、表格、公式）

参与 §9 的层级合并，合并时不跨越 Unit 边界。

### 7.2 代码块

- 不超过 `inline_code_tokens` 的小代码块（一行命令、短配置）当普通文本处理，跟着正文合并。
- 其余代码块单独成 chunk（`type="code"`），前后都强制断开。当前正在累积的文本 chunk 先结束，代码块之后重新开始。
- 引导句：同一节内紧挨在代码块前面的段落，取最后一句（最多 80 token）作为 `meta.lead_in`，只放进代码 chunk 的 `embed_text`，不重复写进 `text`。
- 代码 chunk 和前面的文本 chunk 通过 `related_ids` 互相指向，检索命中其中一个时可以把另一个一起带出来。
- `meta.lang` 记录语言（取自代码块围栏，没有则留空）。
- 超过 max 的代码块按 §8.2 拆分。

### 7.3 超大表格和列表

- 表格超过 max：按行分组拆分，每组都重复表头；caption 放进每一段的 `embed_text`。
- 列表超过 max：按顶层列表项拆分，引导句（冒号结尾的那段）放进每一段的 `embed_text`。
- 拆出来的各部分在 `meta.split_part` 中标记为 `"2/3"` 这种形式。

## 8. 超长单元递归拆分

只对单个 Unit 超过 max 的情况生效。拆出来的每一段都尽量接近 target（而不是 max），这样拆出来的段落大小和普通 chunk 保持一致。

### 8.1 文本

分隔符从粗到细依次尝试：段落（`\n\n`）→ 换行（`\n`）→ 句末标点（`。！？；!?;`）→ 逗号类（`，,、`）→ 按 token 硬切。某一级切完后，还超过 target 的片段继续用下一级切。

```python
import re

# 用零宽的后行断言切分，分隔符留在片段末尾，"".join(pieces) 能还原原文
SEPARATORS = [r"(?<=\n\n)", r"(?<=\n)", r"(?<=[。！？；!?;])", r"(?<=[，,、])"]

def split_text(text: str, target: int, count, level: int = 0) -> list[str]:
    if count(text) <= target:
        return [text]
    if level >= len(SEPARATORS):
        return hard_cut(text, target)          # 按 token 切，最后兜底
    pieces = [p for p in re.split(SEPARATORS[level], text) if p]
    out: list[str] = []
    for p in pieces:
        out.extend(split_text(p, target, count, level + 1))
    return out
```

切完之后片段往往很碎，再贪心拼回接近 target 的段落，相邻两段之间保留重叠：

```python
def repack(pieces: list[str], target: int, overlap: int, count) -> list[tuple[str, int]]:
    """返回 [(段落文本, 开头与上一段重复的字符数), ...]。"""
    parts, buf, size, head = [], [], 0, 0
    for p in pieces:
        n = count(p)
        if buf and size + n > target:
            parts.append(("".join(buf), head))
            # 从上一段末尾往回取完整片段作为重叠，不超过 overlap
            tail, t = [], 0
            for q in reversed(buf):
                if t + count(q) > overlap:
                    break
                tail.insert(0, q)
                t += count(q)
            if len(tail) == len(buf):   # 上一段整段都能当重叠时不重叠，避免整段重复
                tail, t = [], 0
            buf, size, head = tail, t, sum(len(q) for q in tail)
        buf.append(p)
        size += n
    if buf:
        parts.append(("".join(buf), head))
    return parts
```

- 重叠按完整片段（通常是一句话）取，不会从句子中间截断。
- 每段开头重复的字符数写进 `meta.overlap_chars`，[上下文构造](上下文构造.md)合并相邻拆分段时据此去掉重复部分。
- 各段 `meta.split_part` 标 `"i/n"`，`meta.strategy="split"`。
- 片段 token 数直接累加，和整体重新计数会有几个 token 的误差，max 留有余量，可以忽略。

### 8.2 代码

- 按语言的顶层定义切：Python 用 `def` / `class`，JS/TS 用 `function` / `class` / `export`，Go 用 `func` / `type`；其他语言或识别失败时按空行切，再不行按行切。
- 行边界切分原则：优先在行边界切分；单行超过 max 时允许行内切分（见下）。
- **超长行处理**（单行 > max_tokens）：
  - 优先在语法边界切分：`,`、`;`、`{`、`}`、`(`、`)`等
  - 找不到合适语法边界时按 token 硬切，标记 `meta.force_split=true`
  - 这种情况很少见（压缩 JSON、超长字符串、生成代码），标记后可在评测时单独分析
- 每段重新包上 ```` ```lang ```` 围栏，保证每段都是合法的 Markdown 代码块。
- 代码段之间不做重叠；`embed_text` 里带上引导句和 `(续 i/n)`。

## 9. 层级合并

这是切分的核心，对应三种合并方式：
- 完整合并：整节放得下，就整节作为一个 chunk。
- 语义合并：叶子节内，相邻单元语义相近的尽量放在一起，语义断点处优先断开。
- 贪心合并：按顺序累积到 target 为止。

优先级是结构 > 语义 > 贪心：语义和贪心只在结构内部起作用，不会为了凑大小跨越结构边界或拆开单元。

### 9.1 节级：自上而下

```python
def chunk_section(sec: Section) -> list[Draft]:
    # 1. 完整合并：整节放得下（且没有必须断开的大代码块）就整节输出
    if not has_hard_break(sec):
        if sec.tokens <= cfg.target_tokens:
            return [whole(sec, strategy="section")]
        if not sec.children and sec.tokens <= cfg.max_tokens:
            return [whole(sec, strategy="section")]  # 叶子节在 max 内也保持完整

    # 2. 放不下：本节正文作为一个 item，每个子节各作为一个 item
    items = ([Body(sec.body)] if sec.body else []) + sec.children
    drafts: list[Draft] = []
    group: list = []          # 正在凑的一组小 item
    for it in items:
        if fits_whole(it) and group_tokens(group) + it.tokens <= cfg.target_tokens:
            group.append(it)  # 小的正文 / 子节并在一起（相邻兄弟之间的结构合并）
            continue
        drafts += flush(group)
        group = []
        if fits_whole(it) and it.tokens <= cfg.target_tokens:
            group = [it]
        elif isinstance(it, Body):
            drafts += pack_units(it.units, sec.path)   # 叶子级：语义 + 贪心
        else:
            drafts += chunk_section(it)                # 子节太大，递归
    drafts += flush(group)
    return drafts
```

几条规则：
- 叶子节（没有子节）只要不超过 max 就保持完整，不会为了靠近 target 拆开一个完整的小节。
- 有子节的节超过 target 才拆，避免一个 chunk 里塞太多主题。
- 小的相邻兄弟节可以合并，但只在同一个父节下；合并后的 chunk 里保留各子节的标题行，`section_path` 取共同的父节路径。
- 子节一旦需要拆，就单独递归处理，不和兄弟节的内容拼在一起。

### 9.2 叶子级：语义 + 贪心

`pack_units` 按顺序处理一个节的正文单元，决策顺序如下：

1. 当前单元是 `hard_break`（大代码块）：先结束当前 chunk，代码单独输出（§7.2），然后重新开始。
2. 加入后不超过 target：加入。
3. 加入后超过 target 但不超过 max，并且和前一个单元是强关联（结构绑定或语义强相关）：允许超出 target，加入。
4. 其他情况：结束当前 chunk，当前单元开始一个新 chunk。
5. 提前断开：当前 chunk 已经达到 `target × early_flush_ratio`，并且当前单元和前一个单元之间是语义断点，那么即使还放得下也先断开。

### 9.3 语义断点

只有需要拆分的叶子节（超过 max）才计算语义相似度，整节能放下的不计算，节省向量化开销。

- 每个单元用 Visualized-BGE 的文本编码得到向量，计算相邻单元的余弦相似度 `sim[i]`。
- bge-m3 系列的相似度整体偏高，绝对阈值不稳定，所以按本节内的分布做标准化：`z[i] = (sim[i] - mean) / std`。
  - `z ≤ -1.0`：语义断点
  - `z ≥ 1.0`：语义强相关
  - 其他：中性
- 单元数少于 4 个，或 `std < 0.02`（整节语义很均匀）时，不标断点，退化成纯贪心。
- `semantic.enabled=false` 时整体关闭，只用结构 + 贪心，便于对比评测。

### 9.4 收尾

- 过小的 chunk：小于 `min_tokens` 时，在同一节内并入前一个 chunk，前一个放不下（会超过 max）就并入后一个；都放不下就保留。代码 chunk 和图片 chunk 不参与。
- 页码：`page_start` / `page_end` 取 chunk 内所有 Block 页码的最小值和最大值。
- 相邻关系：按 `seq` 顺序填 `prev_id` / `next_id`，只串 text 和 code chunk，图片 chunk 不进入链条。
- `embed_text` 格式：

```
{文档标题} > {section_path 用 " > " 连接}
{代码 chunk：lead_in；拆分段：(续 i/n)}
{text}
```

已确定：每个 chunk 都带着自己所在的标题路径一起向量化（稠密向量和 BM25 都用 `embed_text`）。标题路径放进 `embed_text` 而不是 `text`，这样向量里带有章节语义，但给 LLM 的原文不会重复标题。

- 标题路径超过 4 层时，保留文档标题和最后 3 层；每个标题超过 50 字的截断。
- 整节 chunk 的 `text` 第一行本身就是标题，和前缀里的最后一级相同时，从 `embed_text` 的正文部分去掉这一行，避免重复。
- 没有标题的文档（TXT）只带文档标题。
- 具体例子见[向量化建库](向量化建库.md) §3。

## 10. 图片关联

图片单独成 chunk（`type="image"`），通过元数据指向附近的文本，保证命中图片时能拿到上下文，命中文本时也能带出图片。

### 10.1 锚点

每张图片在 §6 里留下了占位符，合并完成后：
- 锚点 chunk：包含占位符的那个 text chunk。
- 占位符恰好落在代码 chunk 前后（不在任何 text chunk 里）：取同一节内前一个 text chunk，没有就取后一个。
- 整节只有图片没有文字：按文档顺序取最近的 text chunk。

### 10.2 字段

| 字段 | 取值 |
|------|------|
| `type` | `image` |
| `image_path` | `clean/{doc_id}/v{version}/images/xxx.jpg` |
| `text` | caption；没有 caption 时用清洗阶段补充的 `meta.context` |
| `embed_text` | 标题路径 + caption + context，和图片一起送进 Visualized-BGE 编码 |
| `meta.anchor_id` | 锚点 chunk 的 id |
| `related_ids` | 锚点 chunk，以及它的 prev / next chunk（同一节内） |
| `section_path` / `page_start` | 和锚点 chunk 一致；页码用图片自己的 |

反向关联：锚点 chunk 的 `image_ids` 加上这张图片的 chunk_id。

### 10.3 不单独成 chunk 的图片

- 表格截图、公式截图：文字已经在 table / equation 里了，只把路径记到对应 chunk 的 `meta.image_paths`，前端展示用。
- 清洗阶段已经过滤掉的图标、logo、空白图不会出现在这里。

## 11. 去重

- **content_hash**：每个 chunk 的 `text` 归一化（NFKC、去掉所有空白）后计算 sha256，写进 `Chunk.content_hash` 并入库。下面的去重和[检索与重排](检索与重排.md) §4.4 的召回后去重都用它。
- **文档内去重**：同一文档内 `content_hash` 相同的只保留第一次出现的那个可检索，其余标记 `searchable=false`。只标记不删除，这样 `prev_id` / `next_id` 链条不会断。
- **跨文档副本保留可检索**：不同文档的相同内容都保留 `searchable=true`（不入库去重），召回后去重在检索层完成。这样限定文档检索时不会丢失该文档的内容。
- 模板文本：同一段文本出现在超过 `chunking.dedup.boilerplate_doc_count` 个文档里（免责声明、版权页这类），标记 `searchable=false`。
- 图片 chunk：清洗阶段已经按 pHash 去过重，这里不再处理。

## 12. 例子

默认预算 target=400、max=800，某一章的结构和 token 数如下：

```
第2章 部署（共 1500）
├── 正文 80
├── 2.1 环境要求 200
├── 2.2 安装 350
├── 2.3 配置 800（段落A 150、段落B 200、代码块 300、段落C 150）
└── 2.4 验证 70
```

切分过程：
1. 第2章总共 1500，超过 target，而且有子节，拆开处理。
2. 正文 80 + 2.1 的 200 = 280，没超过 target，合成一组；再加上 2.2 的 350 就超了，这一组结束 → chunk 1（正文 + 2.1，`strategy=section`）。
3. 2.2 的 350 没超过 target，开始新的一组；2.3 放不进这一组，2.2 单独输出 → chunk 2。
4. 2.3 是叶子节，但有大代码块（`hard_break`），不能整节保留，进入 `pack_units`：
   - 段落A + 段落B = 350 → chunk 3
   - 代码块单独输出，`lead_in` 取段落B的最后一句 → chunk 4（code），和 chunk 3 通过 `related_ids` 互相指向
   - 段落C 150 → chunk 5
5. 2.4 的 70 单独一组 → chunk 6。它和 chunk 5 属于不同的节，不做过小 chunk 合并。

结果：6 个 chunk，没有任何段落或代码块被拆开，每个 chunk 都不超过 max。

## 13. 验证与评测

单元测试（建议用 hypothesis 做属性测试，随机生成 Block 序列）：
- 所有 chunk 的 `tokens ≤ max_tokens`。
- 覆盖完整：按 seq 把 text 和 code chunk 拼起来（去掉重叠部分和占位符）等于原文。
- 除递归拆分产生的 chunk 外，不存在跨越 Unit 边界的切分。
- 代码 chunk 的每一段都是合法的围栏代码块，没有从一行中间切开。
- 每个图片 chunk 都有 `anchor_id`，并且锚点 chunk 的 `image_ids` 里有它（双向一致）。
- 相同输入重复运行，输出完全一致（chunk_id 确定性）。

统计（每批入库输出）：chunk token 数分布（p50/p90/max），各 `strategy` 占比，过小 chunk 的比例，递归拆分的比例。

检索评测（放在[评估与监控](评估与监控.md)）：固定评测集，对比
- target = 256 / 400 / 600
- 语义断点开 / 关
- 标题路径的深度（完整路径 / 只保留最后 1~2 层）

指标用 Recall@5 / Recall@10 和 MRR。
