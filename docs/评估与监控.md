# 评估与监控

## 1. 目标

- 离线评测：用 LLM 生成的固定评测集，每次改配置、Prompt 或切分参数后跑一遍，和基线对比；关键指标下降超过门槛就不允许上线。
- 阈值校准：前面各篇留下的阈值（grade 通过线、支持度阈值、融合权重等）统一在这里用评测集校准。
- 在线监控：Langfuse 云端记录每次请求的 trace（只记元数据，资料和回答原文遮掉）；Prometheus + Grafana 做指标和告警；收集用户点赞点踩。

参数在 `config.yaml` 的 `eval`、`monitor` 段；评测用模型在 `llm.scenes.eval`。

## 2. 总体结构

```
离线
  eval/generate.py  从索引里抽 chunk → 评测模型出题 → 过滤 → eval/datasets/v1.jsonl
  eval/run.py       快速档 / 完整档 → eval/reports/{时间}.json + .md → 和基线比较 → 退出码
  eval/calibrate.py 阈值校准，输出建议值，人工确认后改 config.yaml

在线
  每次请求 → Langfuse trace（元数据）+ Prometheus 指标
  前端反馈 → POST /api/feedback → SQLite + Langfuse score
```

## 3. 评测集

全部由 LLM 生成，自己写生成器（RAGAS 只用来打分）：RAGAS 自带的出题工具不产出多轮、闲聊、反问、范围限定这类题，也不带我们需要的标签。

### 3.1 题型与数量

| 题型 | 数量 | 生成方式 | 用来评什么 |
|------|------|----------|------------|
| 单段事实 | 300 | 给一个 chunk，出一个只靠它就能回答的问题 | 检索、回答 |
| 跨段 / 跨文档 | 60 | 给同一节或相关的两个 chunk，出一个必须结合两段才能回答的问题 | 多段综合 |
| 没有答案 | 40 | 出和资料领域相关、但资料里没有答案的问题 | fallback、grade 通过线 |
| 多轮追问 | 40 | 基于一个 chunk 出“首问 + 带指代的追问” | 指代消解 |
| 闲聊 | 20 | 模板 + LLM 改写 | 意图路由 |
| 反问 | 20 | 缺少关键信息的模糊问题 | clarify |
| 范围限定 | 20 | 在单段事实题前加“在《标题》里”“PPT 中” | 范围识别 |

单段事实题里再打两个标签，单独统计（前面几篇要求分开看这两类）：
- `keyword`：问题里有错误码、函数名、型号等精确词，看 BM25 权重是否够。
- `image`：答案在图片 chunk 里，看图片召回。

### 3.2 抽样与过滤

- 抽样：按文档分层抽 chunk，每个文档最多 `max_per_doc` 题，保证覆盖面；跳过 `searchable=false` 和少于 `min_chunk_tokens` 的 chunk。
- 出题时要求给出：问题、参考答案、支撑答案的原文片段（`quote`，必须逐字摘自 chunk，至少 20 字）。
- 过滤规则：
  - `quote` 不在 chunk 原文里 → 丢弃。
  - 问题和 `quote` 的字二元组 Jaccard > `max_overlap`（0.5）→ 照抄原文，重新生成，最多 2 次。生成 Prompt 也要求换一种说法、用用户会用的口语。
  - 和已有问题的向量相似度 > 0.95 → 去重。
  - 没有答案题：用当前检索跑一遍，重排最高分 ≥ 0.3 的丢弃（可能其实有答案）。
- 已知偏差：LLM 出的题仍然会偏向原文措辞，检索指标比真实用户问题偏乐观，BM25 尤其明显。门槛按“和基线的变化”判断，受这个偏差的影响较小。

### 3.3 记录格式

```json
{
  "id": "q00042",
  "type": "single",
  "tags": ["keyword"],
  "turns": [{"question": "错误码 E1024 是什么意思？"}],
  "expect": {
    "intent": "rag",
    "standalone": null,
    "scope_doc_ids": [],
    "answerable": true
  },
  "gold": [{"doc_id": "0123456789abcdef", "version": 3, "quote": "E1024 表示连接池已满……"}],
  "reference": "E1024 表示连接池已满，需要调大 max_connections。",
  "gen": {"model": "…", "prompt_version": "eval-v1", "created": "2025-09-30"}
}
```

多轮题的 `turns` 有多条，前面几轮带 `answer`（评测时作为历史），最后一轮是要评的问题，`expect.standalone` 是期望的完整问题。

### 3.4 标准答案不绑定 chunk_id

改切分参数后 chunk_id 会全部变化，而切分参数本身就是要评测的对象，所以标准答案记成“文档 + 原文片段”，评测时再对应到当前索引里的 chunk：

```python
def align(quote: str, chunks: list[dict]) -> set[str] | None:
    """chunks：某文档当前版本的全部 text / code chunk，按 seq 排序。返回覆盖 quote 的 chunk_id。"""
    text, spans = "", []
    for c in chunks:
        body = c["text"][c["meta"].get("overlap_chars", 0):]   # 去掉拆分段的重叠
        spans.append((len(text), len(text) + len(body), c["chunk_id"]))
        text += body
    i = text.find(quote)
    if i < 0:
        return None                          # 文档改过版本，这道题作废，等重新生成
    j = i + len(quote)
    return {cid for a, b, cid in spans if a < j and b > i}
```

- 一个片段可能跨两个 chunk，任意一个进入结果就算命中。
- 文档版本变了、片段找不到的题标记为 `stale`，不参与统计，报告里列出数量。

## 4. 两档评测

| 档位 | 什么时候跑 | 跑哪些环节 | 调用的模型 |
|------|------------|------------|------------|
| 快速档 | 每次改配置、Prompt、切分参数 | 预处理 → 检索 → 重排 → 上下文构造 | 预处理小模型（结果按“问题 + 历史 + prompt 版本 + 模型”缓存） |
| 完整档 | 上线前 | 快速档 + 生成 + 后处理 + RAGAS 打分 | 另加生成模型和评测模型 |

```
python -m eval.run --tier quick|full --dataset eval/datasets/v1.jsonl \
                   [--collection rag_chunks_eval] [--update-baseline]
```

- 默认查线上别名 `rag_chunks`（只读）。
- 比较切分参数时，用 `--collection` 指向一个临时 collection：只包含评测集涉及的文档，外加随机抽的 5% 其他文档作干扰项，避免为了评测重建 1000 万 chunk 的全量索引。
- 评测直接调用各模块，不经过 Langfuse，评测内容不上传到云端。

## 5. 指标

| 环节 | 指标 | 说明 |
|------|------|------|
| 预处理 | intent 准确率 | 单独看知识问题被误判为 chat 的比例 |
| 预处理 | 指代消解 | 多轮题上，完整问题检索和原问题检索的 Recall@8 对比 |
| 预处理 | 范围识别 | 精确率、召回率；重点看识别错导致限定错范围的比例 |
| 检索 | Recall@30（重排前）、Recall@8 / MRR / nDCG@8（重排后） | 按 §3.4 对齐后的 chunk 计算；跨段题按片段算召回 |
| 检索 | 分组统计 | `keyword`、`image` 标签和跨段题分开看 |
| 上下文 | 覆盖率 | 标准答案所在 chunk 进入 `context_blocks` 的比例；因预算被丢弃的命中数 |
| 回答（RAGAS） | 忠实度、回答相关性、上下文精确率、上下文召回率、正确性 | 见 §6 |
| 回答 | 没有答案题的处理 | 进入 fallback 或明确说明资料中没有的比例；答案题被误判为没有答案的比例 |
| 引用 | 有效率、支持率、覆盖率 | 来自后处理的 `gen_meta.post`；答案里没有 `[n]` 时三项记 0，只有校验降级（`verify_degraded`）时支持率才是 None |
| 延迟 | 各阶段 p50 / p95 | 评测机上的数字只用于和基线比较 |

0 分和 None 是两件事：**0 分是测到的失败，None 是没测成**。可答题如果检索或 grade 判定没有支撑（走 fallback、`context_blocks` 为空），五项 RAGAS 指标记 0 分，同时保留 `answerable_rejected=1`；只有生成失败、judge 调用失败、校验降级这类真故障才留 None，并阻止写基线。

## 6. RAGAS 打分

- 版本固定（写进 `pyproject.toml`），RAGAS 各版本接口变化很大。
- 打分模型用 `llm.scenes.eval`（LangChain 的 ChatOpenAI 包一层给 RAGAS）；回答相关性需要的向量用本地编码服务，同样包成 LangChain Embeddings。
- 送去打分的回答先去掉补充说明段和所有 `[n]`（用后处理的解析结果），否则允许补充的内容会被算成不忠实。
- 上下文用 `context_blocks` 的正文，参考答案用评测集的 `reference`。
- 没有答案题不跑 RAGAS，只看 §5 的处理结果（由评测模型判断回答是否明确说明资料中没有）。
- RAGAS 内置的是英文 Prompt。先抽 30 条中文样本，比较 RAGAS 的打分和评测模型直接按同样标准打的分，差异大的话用它的 Prompt 适配功能改成中文再用。
- 评测模型建议和生成模型不同，减少“给自己的回答打高分”的偏差；默认引用 `main`，有条件时在 `llm.scenes.eval` 里换掉。

## 7. 阈值校准

`eval/calibrate.py` 只输出建议值和依据，人工确认后再改 `config.yaml`。

| 参数 | 来源文档 | 用什么数据 | 方法 |
|------|----------|------------|------|
| `grade.pass_score` | 检索与重排 | 有答案题和没有答案题的重排最高分 | 取两类分布分得最开的点（Youden J） |
| `rerank.threshold` | 检索与重排 | 被阈值丢弃的候选 | 看其中有多少是标准答案所在的 chunk |
| `retrieval.weights` | 检索与重排 | 有答案题，`keyword` 单独看 | 稠密权重 0.5~0.8 扫描，看 Recall@30 |
| `retrieval.candidates` / `search_list` | 检索与重排 | 有答案题 | 看 Recall@8 和延迟的取舍 |
| `postprocess.support_threshold` | 后处理 | 完整档的回答；评测模型逐条判断“句子-引用”是否被支持，作为标签 | 取 F1 最高的阈值 |
| `context.token_safety_factor` | 上下文构造 | 抽 1000 个 chunk，各发一次最小请求（`max_tokens=1`） | 用 `usage.prompt_tokens` 减去固定开销，和 `tokens` 字段对比，取 p95 比值 |
| `chunking.target_tokens` 等 | 文档切分 | 临时 collection（§4） | 256 / 400 / 600 各建一次，看 Recall@8 |

## 8. 回归门槛

- 基线：`eval/baselines/{quick,full}.json`，只有加 `--update-baseline` 才会更新（改动被接受后手动执行）。
- 写基线要求两轮每题都没有 `failed`/`partial`、`required_metrics` 没有 None。0 分照常计入并参与门槛比较（见 §5 的 0 与 None 之分），不会因为“答得差”而阻止建基线。
- 报告头部记录：`config.yaml` 的哈希、prompt 版本、评测集版本、collection 名、各场景用的模型、`stale` 题数量。
- 任一项不通过，脚本返回非零退出码，报告里标红：

| 指标 | 档位 | 不通过条件 |
|------|------|------------|
| Recall@8 | 快速 | 下降超过 2 个百分点 |
| 知识问题误判为 chat | 快速 | 超过 2% |
| p95 总延迟 | 快速 | 上升超过 60% |
| 忠实度 | 完整 | 下降超过 0.03 |
| 引用支持率 | 完整 | 下降超过 10 个百分点 |
| 没有答案题的正确处理率 | 完整 | 下降超过 5 个百分点 |

LLM 打分有波动：第一次建基线时把完整档跑两遍，看同一配置两次结果的差异，门槛要明显大于这个波动，否则调大。多次重跑实测：p95 两轮相差 23%–45%，引用支持率相差 0.8–4.8 个百分点，延迟和引用两项门槛按此放宽（记录见 `.planning/L4/m4/20261019-m4-final-baseline.md`）。这两项是为 40 题样本建的临时门槛，471 题全量跑完后必须按全量波动重新收紧；之后再改门槛，要按同样方法重新量一次。

## 9. 在线 trace（Langfuse 云端）

- 接入：LangGraph 调用时传 Langfuse 的 LangChain CallbackHandler，每个节点、每次 LLM 调用自动成为一个 span。
  - `session_id` = 会话 id，trace 元数据带 `message_id`、`config_hash`、`prompt_version`、`intent`。
  - 地址和 key：`monitor.langfuse.host`、`public_key_env`、`secret_key_env`；key 放环境变量。
  - 区域（EU / US）按数据合规要求选。
- 上报失败不影响主流程：SDK 在后台批量发送，失败只记本地日志。

### 9.1 遮掉原文

trace 会发到云端，默认只保留元数据：字典里不在白名单中的字符串一律替换成 `[masked:长度]`，数字、布尔原样保留。用户问题、资料正文、Prompt、回答都会被遮掉。

```python
KEEP = {"chunk_id", "doc_id", "version", "seq", "type", "intent", "status", "endpoint",
        "model", "prompt_version", "finish_reason", "cite", "state", "stage", "scene"}

def _mask(x, key=None):
    if isinstance(x, dict):
        return {k: _mask(v, k) for k, v in x.items()}
    if isinstance(x, list):
        return [_mask(v, key) for v in x]
    if isinstance(x, str) and key not in KEEP:
        return f"[masked:{len(x)}]"
    return x

def mask(*, data, **_):          # 传给 Langfuse(mask=...)；签名以所用 SDK 版本为准
    return _mask(data)
```

- 完整 Prompt / 回答抽样**只写本地**：生成节点按 `logging.prompt_sample_rate` 决定是否记录，将完整 PromptPackage、回答、状态写入 `logging.sample_path` 的 JSONL；单文件大小和历史份数由 `logging.sample_max_mb` / `logging.sample_keep_files` 控制，关闭时不创建文件。文件仅用户可读写，写盘失败只记异常类型，不影响回答。
- 不创建、不切换“无遮掩”的 Langfuse 客户端；无论抽样比例如何，云端始终只收遮掩后的元数据。原文不新增到图状态或 checkpoint。
- Langfuse 云端的数据保留期在 Langfuse 后台设置；本地运行日志保留期交给 journald，抽样文件按大小/份数轮转。部署见[服务化部署](服务化部署.md) §8。

## 10. Prometheus 指标与告警

应用在内网暴露 `/metrics`，Prometheus 抓取，Grafana 展示。D-013 B 保留原 LLM 函数签名，指标通过 `llm.observability.METRICS` 进程全局入口访问；API lifespan 绑定该对象，关闭或初始化失败时恢复。每个服务进程只运行一个活动 API 应用；测试用 monkeypatch 替换全局对象，离线评测可用 `metrics_scope(None)` 暂停并在退出时恢复。该上下文不是并发请求级隔离，Deps 不接收 metrics/message_id 构造参数。各指标如下：

| 指标 | 类型 | 标签 |
|------|------|------|
| `rag_requests_total` | counter | `route`（rag / chat / clarify / fallback）、`status` |
| `rag_stage_seconds` | histogram | `stage`（preprocess / retrieve / rerank / build_context / ttft / generate / postprocess） |
| `rag_llm_calls_total` | counter | `scene`、`endpoint`、`outcome`（ok / retry / fallback / failed） |
| `rag_llm_tokens_total` | counter | `scene`、`endpoint`、`kind`（input / output） |
| `rag_degraded_total` | counter | `kind`（preprocess / rerank / hybrid / verify / image） |
| `rag_retries_total` / `rag_fallback_total` | counter | — |
| `rag_citations_total` | counter | `state` |
| `rag_feedback_total` | counter | `rating` |

- 标签只用固定取值，不放会话 id、用户 id，避免标签基数爆炸。
- 基础设施：Milvus 真实内存指标为 `process_resident_memory_bytes{job="milvus"}`；本机 nvidia-smi exporter 输出 `rag_gpu_memory_used_bytes` / `rag_gpu_memory_total_bytes`，显存比率由二者相除。监控栈生成器和看板见[服务化部署](服务化部署.md) §10，参数统一在 `monitor.stack`。

告警阈值写在 `config.yaml` 的 `monitor.alerts`，由 `scripts/gen_alerts.py` 生成 Prometheus 的规则文件，保持“参数只在一处”：

| 告警 | 默认条件 |
|------|----------|
| 首字延迟高 | ttft p95 > 6 s，持续 10 分钟 |
| 报错率高 | 失败请求占比 > 2%，持续 5 分钟 |
| 备用模型用得多 | fallback 占 LLM 调用 > 10%，持续 15 分钟 |
| 降级多 | 任一 `rag_degraded_total` 占请求 > 5%，持续 15 分钟 |
| Milvus 内存 | 常驻内存 > 10 GB，持续 10 分钟 |
| 显存 | GPU 显存占用 > 90%，持续 10 分钟 |
| 点踩率高 | 1 小时内点踩占反馈 > 30%（反馈数 ≥ 20 时才判断） |

## 11. 用户反馈

- 会话来源：问答 `POST /api/chat` 可从 body `session_id` 或 `X-Session-ID` 取会话，同传必须一致；反馈仅从 `X-Session-ID` 取会话，与问答使用同一 checkpointer 查询只读历史。会话标识不是用户身份凭证。
- 接口：`POST /api/feedback`，`{"message_id": "...", "rating": 1 | -1, "reason": "可选，最多 500 字"}`。
  - `message_id` 必须存在于该会话的历史里（后处理保存本轮时写入），否则拒绝；按会话限流。
  - 系统目前没有用户鉴权，反馈接口和问答接口一样，靠部署在内网控制访问。
- 本地保存：`paths.feedback_db`（SQLite），字段 `message_id`、`session_id`、`rating`、`reason`、`created_at`。
- Langfuse：只上报分数（`rating`），挂到对应 trace 上；`reason` 是用户原文，只存本地。
- 点踩的回答每周导出一次清单（问题、回答、引用状态、各阶段耗时），用于排查问题。

## 12. 安全与合规

- Langfuse 云端只收到遮掩后的元数据；完整 Prompt / 回答抽样只写本机受控目录，不上传云端，打开前确认本地磁盘权限、容量与合规。
- `/metrics` 只在内网开放，不经过对外网关。
- `eval/datasets/` 和 `eval/reports/` 里有资料原文片段，按资料的敏感程度决定是否提交到代码仓库；默认加进 `.gitignore`。
- 所有 key（评测模型、Langfuse）放环境变量，不写进 `config.yaml`。

## 14. 验证

- `align`：片段落在一个 chunk 内、跨两个 chunk、在拆分段重叠区域；文档改版后返回 `None`。
- 过滤：照抄原文的问题被丢弃；`quote` 不在 chunk 里的被丢弃。
- `mask`：白名单字段保留，其余字符串全部遮掉，嵌套字典和列表也生效。
- 门槛：构造一份比基线差的报告，脚本返回非零退出码。
- 第一次建基线时完整档跑两遍，确认波动小于门槛（§8）。
