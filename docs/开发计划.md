# 开发计划

本文是设计文档到代码之间的施工计划：怎么起步、几个人怎么分、哪些接口先冻结、每个里程碑的验收标准。
系统的行为、参数含义、字段定义仍然以各设计文档为准，本文只讲顺序和边界。

## 1. 结论

- **不能直接并行**。项目还没有 `pyproject.toml`，也没有任何跨模块契约的代码载体。先串行做一个薄薄的「共识层」（P0），之后四条线的并行才是真的并行。
- P0 产出的是**接口、夹具和桩**，不是功能。它本身的业务逻辑几乎为零，但它决定了后面四个人会不会互相改对方的数据结构。
- 分工按**依赖关系**切，不按「离线 / 在线」切。在线链路模块数远多于离线，按离线/在线切会严重不均。
- 四个 LLM 接入点的 `base_url` / `model` / key 曾是唯一的硬阻塞项，谁都没有替代方案（2026-10-19 已解决，见 §7）。

## 2. 为什么先做 P0

`总揽.md` §7 里已经写死的跨文档契约都是**接口**：

| 契约 | 出处 | 谁写 | 谁读 |
|------|------|------|------|
| `chunk_id` 格式、`tokens` / `section_idx` / `prev_id` / `image_ids` / `searchable` | 文档切分 §4 | 切分 | 建库、检索、上下文、评测 |
| `embed_text` = 标题路径 + 正文 | 向量化建库 §3 | 切分 | 建库、BM25 |
| Milvus collection 字段与索引定义 | 向量化建库 §5 | 建库 | 检索 |
| `build_expr` 的过滤白名单 | 检索与重排 §4.2 | 检索 | 预处理（软过滤）、API（硬过滤） |
| `ContextBlock.cite` | 上下文构造 §8 | 上下文 | Prompt 组装、后处理 |
| `escape_tags` 的 `RESERVED` 列表 | Prompt 组装 §5 | Prompt | 所有 `.j2` 模板 |
| `RAGState` 的 21 个字段 | 总揽 §4.1 | 图 | 所有节点 |
| `llm.endpoints` / `llm.scenes` 的结构 | 大模型生成 §3 | LLM 层 | 所有调用方 |

这些接口只要还停留在 markdown 里，同时开工的两个人就会各自发明一套字段名，然后在联调时发现对不上。P0 把它们变成 pydantic 模型、样例 JSON 和契约测试——**改字段就会红**，这才是并行的前提。

## 3. P0：骨架、契约与桩

**串行做，一人负责，4~6 人天。这期间其他人不写业务代码**，可以先读文档、准备测试数据、挑评测样本。

### 3.1 骨架

- `pyproject.toml`：uv + Python 3.12，依赖按技术栈装（langgraph、langchain-openai、pymilvus、fastapi、jinja2、pyyaml、rapidfuzz、pydantic、pytest）。
- `src/ragagent/` 下按 `总揽.md` §6 建包：`ingest/`（含 `chunking/`）、`index/`、`retrieval/`、`preprocess/`、`context/`、`prompt/`、`llm/`、`postprocess/`、`graph/`、`api/`、`monitor/`。
- `src/ragagent/config.py`：`config.yaml` → pydantic 模型，带 `大模型生成.md` §3 的启动校验（`base_url` / `model` 非空、`api_key_env` 指向的环境变量存在、非本机地址必须 https、场景引用的接入点存在，任一不满足直接拒绝启动）。
- `tests/` 骨架 + pytest 配置 + CI 入口（一个 Makefile 目标即可，不要引入额外框架）。

### 3.2 契约落成代码

每个包一个 `models.py`，字段和设计文档逐字对齐：

```
src/ragagent/ingest/models.py          # Block、CleanDocument（数据清洗 §6）
src/ragagent/ingest/chunking/models.py # Chunk、Section、Unit、Draft（文档切分 §4）
src/ragagent/index/models.py           # ChunkFields、ChunkRow、EmbedItem 等（向量化建库 §4.2 §5.1）
src/ragagent/retrieval/models.py       # Hit、Expansion、RetrievalResult（检索与重排 §4.5）
src/ragagent/context/models.py         # ContextBlock、ImageRef（上下文构造 §8）
src/ragagent/preprocess/schema.py      # Preprocessed、Scope、Rewrite（用户问题预处理 §5.2）
src/ragagent/prompt/models.py          # PromptPackage、Message、TextPart、ImagePart
src/ragagent/graph/state.py            # RAGState，21 个字段一次定完（总揽 §4.1）
```

两条纪律：

- `chunk_id` 的构造和解析各写一个函数（`make_chunk_id` / `parse_chunk_id`），加单元测试覆盖 `{doc_id}:v{version}:{seq:05d}`，以及 `doc_id` 的 16 位十六进制正则校验。
- `graph/state.py` 是全员共享的，**只有 P0 负责人能改**，其他人提需求。

### 3.3 夹具与契约测试

`tests/fixtures/` 放真实形状的样例数据，配一组契约测试（改字段就红）：

- `blocks.json`：5 条 Block，覆盖段落、标题、表格、代码、图片。
- `chunks.jsonl`：5 条 Chunk，覆盖文本、代码、图片、拆分段（带 `meta.overlap_chars`）、整节合并。
- `hits.json`：10 条 Hit，含 `prev_id` / `next_id` 链和 `content_hash` 重复项各一组。
- `context_blocks.json`：3 个 ContextBlock，带 `cite` 编号和 `chunk_ids`。
- `preprocess_out.json`、`rewrite_out.json`：预处理和改写的结构化输出样例。
- `answers/`：3 段带 `[n]` 引用的模型回答，其中一段含代码块、一段含补充说明标题。

### 3.4 三个桩

桩是让 L2 / L3 / L4 不等 GPU、不等 API key 的前提，必须和真实现同接口：

| 桩 | 替换 | 行为 |
|----|------|------|
| `tests/stubs/embed_server.py` | Visualized-BGE 编码服务 | 文本 hash → 可复现的 1024 维归一化向量；同义改写不保证相近，只保证确定性 |
| `tests/stubs/rerank_server.py` | bge-reranker-v2-m3 | 按词重叠度打分，支持 `/rerank` 的批量输入和 `max_length` 参数 |
| `tests/stubs/llm_server.py` | OpenAI 兼容接口 | 流式 + 非流式、tool call 结构化输出、可注入 429 / 5xx / 首字超时；返回内容从 `tests/fixtures/answers/` 里取 |

三个桩都用 FastAPI 起本地端口，走和真实服务一样的 HTTP 协议，这样切换只改 `config.yaml` 里的地址。

### 3.5 Milvus 建表验证

- `milvus.yaml` 的 DISKANN 参数、mmap 设置按 `向量化建库.md` §6 落实，连同 `create_collection` 一起跑通。
- 用假 embedding 写入 1000 条，建索引，跑通一条 hybrid search。
- 这一步顺带回答 `向量化建库.md` §12 里最贵的两个问题：BM25 的 `SPARSE_INVERTED_INDEX` 能否 mmap、PQ 比例减半后召回是否可接受。

### 3.6 P0 验收

- [x] `uv run pytest` 全绿，契约测试覆盖 §3.2 的所有 `models.py`。
- [x] `config.py` 能在 `base_url` 为空时报错退出，也能在填好桩地址后正常加载。
- [x] 三个桩都能独立起服务，并有冒烟测试各打一次。
- [x] Milvus 容器起来，1000 条假数据写入 + hybrid search 出结果。
- [x] `graph/state.py` 的字段与 `总揽.md` §4.1 逐条对齐，评审过（契约测试按 AST 逐字比对；P0 之后四条线都没改过它）。

## 4. 四条并行线

P0 完成后四条线同时开工，各线独占自己的目录。

### L1 离线入库

- **范围**：`ingest/`（清洗、切分）、`index/`（编码、建库、登记表）。
- **依赖**：MinerU 外部服务、GPU、Milvus（L2 先启动容器）。
- **风险**：关键路径上最慢的一段，因为卡在外部服务；GPU 还要和在线编码服务错开。
- **首日动作**：不等文档收集齐，先拿 PDF / Word / PPT / 图片各一份小文件把 `mineru/client.py` + `convert.py` 打通。

### L2 检索与上下文

- **范围**：`retrieval/`、`context/`、`preprocess/`、`graph/nodes/{retrieve,rerank,build_context,routes,preprocess,clarify,rewrite}.py`（D-004）。
- **依赖**：Milvus（空表也能开发）、假 embedding、假 rerank。
- **说明**：`build_expr` 的白名单校验要放在第一批做，它是唯一允许用户输入接触 Milvus 表达式的地方，越早定越好。

### L3 生成链

- **范围**：`llm/`、`prompt/`、`postprocess/`、`graph/{build,deps}.py`、`graph/nodes/{generate,postprocess,fallback}.py`、`api/{sse,app}.py`（D-004）。
- **依赖**：只要假 LLM 和夹具，**不依赖 Milvus、不依赖 GPU**——这是最独立、最容易出成果的一条线，建议第一个开工。
- **说明**：`escape_tags` 的 `RESERVED` 列表要和 `prompts/v1/*.j2` 里的实际标签做一次交叉检查，写成测试（扫模板文件里的标签名，逐个断言在 `RESERVED` 里）。

### L4 评测与监控

- **范围**：`eval/`、`monitor/`（含反馈路由和指标）；由 L3 API 主程序挂载（D-004）。
- **依赖**：假 LLM（出题和打分）、夹具。
- **说明**：第一天就开。它的作用是让后面所有阈值调整有依据；没有它，`grade` 的 0.5、`support_threshold` 的 0.3、融合权重 0.7/0.3 全都是拍脑袋。
- **首日动作**：出题器 + Recall / MRR / nDCG 骨架 + 用夹具跑通一遍两档评测的壳。

## 5. 依赖图

```
              P0（骨架 + 契约 + 桩 + Milvus 建表）
                            │
        ┌───────────┬───────┴───────┬───────────┐
        │           │               │           │
   L1 离线入库   L2 检索与上下文   L3 生成链   L4 评测与监控
   （MinerU/GPU）  （Milvus）      （无外部依赖）（假 LLM）
        └───────────┴───────┬───────┘           │
                            │                   │
                    L2 联调（真实数据 + 真 embedding）
                            │
                     阈值校准（用 L4 的评测集）
                            │
                       M5 API 服务化与部署
                       （锁 / 探活 / 备份 / 本地抽样 / 监控栈）
                            │
                       前端重写 → 调优（重跑基线）
```

交汇点只有两个：**Milvus collection 字段**（L1 写、L2 读）和 **`RAGState`**（全员读）。两个都在 P0 冻结，之后各线互不阻塞。

关键路径是 **L1 → L2 联调 → 阈值校准**。L3 / L4 是资源池，谁空了谁补。

## 7. 阻塞项

外部阻塞已清空（2026-10-19）：四个接入点切到 `wangzi.us` 的 `gpt-6-luna`；MinerU 云端解析质量已人工确认；主机内存 30 GB，Milvus 实占约 2.7 GiB。剩下的都是内部待办，不卡排期。

| 项 | 状态 | 说明 |
|----|------|------|
| 评测模型接入点 | 推后 | 生成和打分现在是同一个模型，指标偏乐观（`评估与监控.md` §15）。调优时再换第二个模型。 |
| 471 题全量基线 | 推后 | M4 用 40 题分层样本通过（§6）；M5 新配置改变 config_hash，现有基线属旧版，不回填新哈希。调优阶段用独立评测模型重跑全量并按波动收紧 p95 门槛。 |
| 会话库清理 | 不做清理 | 没有界面，也不是 C 端产品，接受会话库增长；需要时手工删 `paths.session_db`，不加删除接口、不做自动清理。 |

单个请求不会无限挂起：LLM 调用、Milvus 调用、编码服务 HTTP 都有超时，等信号量也被首 token 预算包住。会冻结整个进程的是事件循环里的同步 SQLite——已修（2026-10-19）：

- `/api/feedback` 写反馈库是 rollback journal + `BEGIN IMMEDIATE`，写锁竞争时按 busy timeout 阻塞，是最危险的一处，现在走 `asyncio.to_thread`。
- `/api/docs`、`/api/docs/{doc_id}/file`、`/api/images/...` 的登记表查询，以及 `preprocess_question` 里的 `resolve_scope`，同样挪到线程里。登记表是 WAL，读本来就不会被写者挡住，这几处改的是"不占事件循环"，不是"不再阻塞"。

另外两处慢和报错也已处理（2026-10-19）：`/api/chat` 加了整请求上限 `api.request_timeout_s`，超时发 `error` 事件并结束流，单题不再可能拖到几分钟；`retrieval.timeout_ms` 从 1 秒放到 10 秒，编码服务在 GPU 争用时不再直接抛 `RetrievalUnavailable`（此前 16 并发实测 5/40 失败）。代价是检索真卡住时最多等 10 秒，而且这两项都会改变线上延迟分布，M4 基线是按旧值跑的，重跑时再对齐。

## 8. 协作纪律

- 一人一条线，目录不交叉；`graph/nodes/` 按文件分，一人一个文件。
- **`config.yaml`、`graph/state.py`、`tests/fixtures/` 只由 P0 负责人改**，其他人提需求。
- 改任何契约字段时，同一次提交改完所有引用方和夹具，契约测试必须绿。
- 每条线自己跑 `uv run pytest`，跨线的联调测试放在 `tests/integration/`，按 D-004 和并行协作协议由 L3 维护。
- 新增可调参数一律进 `config.yaml`；设计文档只解释含义，不贴带值的 YAML。
